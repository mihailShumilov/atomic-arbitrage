# Модель данных

Схема: `sql/001_schema.sql` + миграции `sql/NNN_*.sql`. Изменения схемы — новым файлом миграции, не правкой старого.

## Схема и миграции

С задачи 023 (2026-10-02):
- **Применение — только `sql/apply.sh`**, к работающему ClickHouse по HTTP (`127.0.0.1:${CLICKHOUSE_HTTP_PORT:-18123}`, пароль из `.env`). `docker-entrypoint-initdb.d` больше не используется: он выполнялся только на пустом томе и ничего не записывал (из-за этого 002 не была применена к локальному тому). Порядок: `docker compose up -d clickhouse`, затем `sql/apply.sh`. Опции: `--dry-run` (список ожидающих), `--to N`.
- **Журнал — `hood.schema_migrations`** (`version`, `name`, `sha256`, `outcome` = `applied`/`skipped`, `applied_at`). Записанная миграция не запускается повторно. Если файл записанной миграции изменился (sha256), скрипт останавливается: применённые миграции неизменяемы, исправление — новым файлом. Второй прогон печатает `changes: 0`.
- **Каждая миграция идемпотентна сама по себе** (`IF NOT EXISTS`, надмножество enum, проверки), чтобы прерванный прогон можно было просто повторить. Если идемпотентность через DDL невозможна (пересоздание таблицы), в файле есть строка `-- apply-unless: <SQL, возвращающий число>`: ненулевой результат значит «схема уже в целевом состоянии», файл пропускается и пишется как `skipped`. Ошибка этого запроса или нечисловой ответ останавливает прогон, в журнал ничего не пишется (ревью 023, Б1). Офлайн-тест скрипта — `bash sql/test_apply.sh` (поддельный `curl`, ClickHouse не нужен). Параллельно два `apply.sh` не запускать: блокировки нет.
- **Пересоздание таблицы никогда не удаляет данные молча**: перед переименованием и `DROP` — `throwIf` на строки и detached-части старой таблицы. Непустую таблицу переносит отдельная миграция с копированием данных.
- **`EXCHANGE TABLES` не использовать — только два обычных `RENAME TABLE`.** На bind-монтировании Docker Desktop (macOS, fs `fakeowner`; так смонтирован `data/clickhouse`) `EXCHANGE` потерял файл метаданных таблицы: в памяти таблица была, после рестарта исчезла. Проверено 2026-10-02 на 26.9.6.6: воспроизведено на временном bind-монтировании и на локальном томе; `RENAME` на том же монтировании переживает рестарт. На docker named volume `EXCHANGE` работает, поэтому проверки миграций делать на bind-монтировании, как у рабочего тома, и с рестартом контейнера.
- **`CREATE OR REPLACE TABLE` и `REPLACE TABLE` тоже не использовать** (задача 029). Проверено 2026-10-03 на 26.9.6.6, временный контейнер с bind-монтированием каталога scratchpad (fs `fakeowner`): обе команды вернули `Code: 1001 … filesystem error: in rename: No such file or directory [store/…/_tmp_replace_….sql] [metadata_dropped/…]`, но замену при этом уже сделали (схема новая, строка старой таблицы пропала). До рестарта в `system.tables` висели «призраки» `_tmp_replace_*` без файлов метаданных; после рестарта каталоги данных старых таблиц (у одной — с частью `all_1_1_0`) остались в `store` сиротами. Та же ошибка переименования в `metadata_dropped` есть в логе локального сервера при аварии `EXCHANGE` в 023. Обычный `DROP TABLE … SYNC` на том же монтировании каталог убирает полностью (проверено там же). `sql/apply.sh` отказывается выполнять файл, если какой-то его стейтмент начинается с `EXCHANGE`, `CREATE OR REPLACE` или `REPLACE TABLE` (проверка до отправки первого стейтмента файла; тест — `sql/test_apply.sh`).
- **Остатки неудачного пересоздания.** После падения на `RENAME` остаётся пустая `<t>_NNN` (её `CREATE … IF NOT EXISTS` выполняется раньше): у 003 это `hood.funding_edges_003`, у 004 — `hood.<t>_004`. Это безопасно: guard из-за неё даёт 0, следующий прогон проверяет, что она пуста, и переиспользует её; при ручной уборке её видно. В комментарий самого 003 это не дописано: 003 уже в журнале локального тома, применённые миграции неизменяемы (sha256), поэтому описание — здесь и в шапке 004.
- **Сироты в `data/clickhouse/store`.** Каталог, которого нет ни у одной таблицы, ClickHouse сам прячет через час (`database_catalog_unused_dir_hide_timeout_sec` = 3600: снимает права, в логе `Removing access rights for unused directory … (will remove it when timeout exceed)`) и удаляет через 30 суток (`database_catalog_unused_dir_rm_timeout_sec` = 2592000). Так было со `store/fb1/fb1c8399-…` (бывшая `funding_edges_003` из 023): спрятан 2026-10-02 19:04 UTC, удалён вручную в задаче 029 при остановленном сервере (внутри только `format_version.txt` и пустой `detached/`). Удалять руками — только при остановленном ClickHouse и если его лог подтверждает, что каталог не используется.
- Образ ClickHouse закреплён в `docker-compose.yml` (`26.9.6.6` — версия, создавшая локальный том, `SELECT version()` 2026-10-02). Обновление — сменой тега, затем `sql/apply.sh` и `DESCRIBE`.
- Миграции: `001_schema.sql` — исходная схема; `002_funding_edges_l1.sql` — колонки входов с L1 (задача 017); `003_funding_edges_key.sql` — новый ключ `funding_edges` (ниже); `004_types_keys.sql` — типы колонок, ключ `labels`, версия `feed_gaps` (ниже).

**Ключ `funding_edges` (003):** `ReplacingMergeTree ORDER BY (to_addr, block_number, tx_index, kind, log_index)`. Ключ сортировки здесь же — ключ дедупликации, поэтому в нём `kind` (рёбра разных видов в одной tx: `l1_eth` и будущий `eth` по `tx.value`) и `log_index` (несколько `DepositFinalized`/WETH-`Transfer` одному получателю в одной tx). `log_index UInt32 DEFAULT 4294967295`: позиция лога в блоке; **4294967295 (`u32::MAX`) = ребро уровня tx** (`0x64`, ETH-`0x68`, обычный `tx.value`), не 0 — 0 это валидный индекс первого лога блока. Порядок колонок — как в 001 + 002 (`log_index` после `tx_hash`) и равен `FundingEdge::COLUMNS`, это проверяет тест `rows::tests::funding_edges_column_order_in_sql_equals_columns` в `crates/decoders`. Колонка не Nullable: Nullable-колонку нельзя держать в ключе без `allow_nullable_key` (в 002 она была `Nullable(UInt32)` — совместимость с 002 сломана, таблица была пуста). Значения Enum8 `kind` и `gateway_status` не менялись. Рёбрам `internal` (трассировки) понадобится свой дискриминатор (`trace_index`), когда появятся трассировки.

**Типы и ключи (004, задача 029):** все таблицы, кроме `funding_edges` (её ключ — 003) и `blocks`, пересозданы так же, как в 003 (отказ на непустой таблице, `<t>_004` + два `RENAME`, `DROP … SYNC`); имена и порядок колонок — как в 001.
- **Пустое значение — `''` / `0` через `DEFAULT`, а не `NULL`** (правило `schema-types-avoid-nullable`): `txs.to_addr` (`''` = создание контракта), `logs.topic1..topic3` (`''` = топика нет), `swaps.router`, `wallets.first_funder` и `first_funding_wei` (`''` = финансирование не найдено), `wallets.first_funding_block` (`0` = не найдено). Фильтровать `!= ''` / `> 0`, а не `IS NOT NULL`.
- **Исключение: `blocks.feed_recv_ns` остаётся `Nullable(UInt64)`**: `NULL` здесь смысловой (блок не пришёл через recorder), см. «Соглашения».
- `txs.selector` — `LowCardinality(String) DEFAULT ''` (`0x` + 4 байта; `''`, если input короче 4 байт). Был `FixedString(10)`, где `''` хранился как 10 нулевых байт.
- `venue` — один тип в `swaps` и `tokens`: `Enum8('pons_v1' = 1, 'pons_v2_curve' = 2, 'uni_v3' = 3, 'uni_v4' = 4, 'pools_trade' = 5, 'other' = 9)`. Новая площадка — миграцией `MODIFY COLUMN` с надмножеством значений в обеих таблицах; неизвестное значение при вставке — ошибка (`Code: 691 … Unknown element`).
- `labels`: `ReplacingMergeTree(updated_at) ORDER BY (address, label, source)` — одна и та же метка от двух эвристик хранится двумя строками; внутри `(address, label, source)` побеждает последняя по `updated_at` (разрешение 1 с).
- `feed_gaps`: `ReplacingMergeTree(filled)` — при слиянии `filled = 1` побеждает `0` независимо от порядка вставки, повторная загрузка `gaps.tsv` с `filled = 0` не «откроет» закрытую дыру. Проверено 2026-10-03 на временном контейнере: вставка `(10, 20, filled 1)`, затем `(10, 20, filled 0)`, после `OPTIMIZE FINAL` осталась строка с `filled = 1`.
- Суммы uint256 остаются десятичной строкой (`value_wei`, `*_raw`, `first_funding_wei`); переход на `UInt256` — решение Михаила.

## Слои

1. **Сырой фид**: `data/feed/YYYY/MM/DD/feed-YYYYMMDD-HH.tsv.zst`. Строка: `recv_unix_ns \t seq_first \t seq_last \t <JSON конверта как есть>`. Неизменяем. После перезапуска recorder дописывает новый zstd-фрейм в тот же часовой файл: читать с поддержкой нескольких фреймов (`zstd -dc` умеет; в Python `stream_reader(..., read_across_frames=True)`).
   - С задачи 002, 2026-09-30, recorder закрывает zstd-фрейм не реже раза в 60 с, поэтому фреймов в часовом файле много.
   - Строки с `seq_first = seq_last = 0` — обычное дело, и при разборе их нужно пропускать или разбирать отдельно:
     - конверты без `messages`, например `{"version":1,"confirmedSequenceNumberMessage":{"sequenceNumber":N}}`;
     - нетекстовые фреймы (ping и др.) в обёртке recorder: `{"recorderFrame":{"opcode":"ping","payloadBase64":"…"}}`. Ключа `recorderFrame` в фиде не бывает;
     - текстовый фрейм, который не парсится как JSON: с задачи 008 (2026-09-30) — в той же обёртке с `"opcode":"text"`, байты текста в `payloadBase64` без изменений. До 008 такой текст писался как есть, с вырезанными `\n`/`\r` (на записанных данных таких строк 0);
     - валидный JSON, который не похож на конверт (например, `messages` не массив), — как есть.
   - Столбец JSON всегда валидный JSON. Из него удаляются только `\n`, `\r` и `\t`. В валидном JSON эти символы могут быть лишь незначащими пробелами между токенами: внутри строк управляющие символы запрещены (RFC 8259, разд. 7). Поэтому значение не меняется, а в строке всегда ровно 4 TSV-поля. `\t` удаляется с задачи 009 (2026-10-01, замечание Р2 аудита 008); раньше он оставался, но на данных 001–002 таких строк 0 из 11 983. Делить строку всё равно надёжнее не более 3 раз (`split('\t', 3)`).
   - **Повторы seq в сырье возможны, дедупликация — обязанность разбора и загрузчика.** Recorder пропускает конверт целиком (счётчик `dup_skipped`), только если все его seq ≤ уже записанного. Конверт, который частично перекрывает записанное (`seq_first ≤ last_seq < seq_max`), пишется целиком, как пришёл: сырьё не режется. Поэтому при разборе ключ блока — `sequenceNumber`; какое вхождение брать при повторе, решает загрузчик (правило описать в его задаче). Расхождение `blockHash` у повторов — ошибка данных, о ней надо сообщать. На данных 001–002 таких конвертов 0: в каждом конверте было ровно 1 сообщение. `feed-audit` считает повтор seq ошибкой (FAIL), так что такой случай будет виден.
   - Рядом с сырьём лежат:
     - `gaps.tsv`: `from \t to \t recv_ns`. Строка дыры публикуется (append + fsync) только вместе с коммитом, который сделал строку данных после дыры долговечной, и никогда раньше неё. С задачи 025 (2026-10-02) это верно и при смене часа: до 025 строка дыры для первой строки нового часа уходила с коммитом прошлого часа, пока сама строка была ещё в открытом фрейме (после kill -9 в этом окне оставалась лишняя строка дыры, безвредно);
     - `last_seq.txt`: последний seq, уже записанный на диск (fsync);
     - `connections.tsv`: события соединения и паузы, первая строка — заголовок. С задачи 021 формат (имена событий, столбцы, строки) задан в одном месте — `crates/recorder/src/connlog.rs`, его фиксирует golden-тест; разбор строки сырья при восстановлении — `rawline.rs`, правило last_seq / устаревший конверт / дыры — `seqtrack.rs`. Столбцы: `ts_utc, ts_unix_ns, event, reason, http_status, retry_after, pause_s, session_s, envelopes, strikes, detail`. У строк первого запуска 002 нет столбца `strikes` (10 столбцов вместо 11). События:
       - `connected` — апгрейд прошёл. С задачи 009 в `detail` после URL идут `requested=<N|->` и `mode=<header|no_data|disabled>`. `header` — отправлены `Arbitrum-Feed-Client-Version: 2` и `Arbitrum-Requested-Sequence-Number: N`, где N = last_seq + 1. last_seq берётся из памяти процесса, а при старте — из данных (`recover`), не из `last_seq.txt`. `no_data` — данных нет, заголовки не отправлялись. `disabled` — задан флаг `--no-requested-seq`;
       - `backlog` (с задачи 009) — статистика бэклога соединения. Бэклог — кадры с seq до первого «живого» кадра, то есть кадра, у которого самое новое `header.timestamp` среди сообщений kind 3 отстаёт от времени приёма меньше чем на 2 с. Сам живой кадр в бэклог не входит. Правило зависит от часов (NTP); kind 9/13 не учитываются, у них время L1-inbox. Правило «до первой паузы > 30 мс» не годится: в живой проверке 009 бэклог шёл с паузами до 99 мс. Строка пишется один раз: `reason=done`, когда пришёл живой кадр, или `session_ended`, если соединение кончилось раньше. `envelopes` — число блоков бэклога, `session_s` — время от первого кадра до живого. В `detail`:
         - `requested`, `last_seq_before`, `first_seq` (первый полученный seq);
         - `first_minus_requested`: 0 — сервер начал с запрошенного; > 0 — начал позже, тогда в `gaps.tsv` будет дыра;
         - `first_lag_ms`, `backlog_blocks`, `backlog_end_seq`, `live_seq`, `live_lag_ms`, `live_after_ms`;
         - `stale_frames` — кадры, где все seq ≤ last_seq; их пропускает writer, это `dup_skipped`;
         - `complete`.

         Без заголовка первый кадр уже живой, `backlog_blocks` = 0. Статистика пишется отдельной строкой, а не столбцами `connected`, потому что `connected` должен попасть на диск сразу после апгрейда: это граница сессии, от которой ищется её конец для `--min-connect-interval-secs` (см. `startup_wait`). В `data/feed-test-009` **обе** строки `backlog` записаны ещё старым бинарником (правило пауз > 30 мс, поля `burst_ms`/`pause_ms`): сессия A — 4 блока вместо 0, сессия B — 6 вместо 621 (проверено тестом `resume::tests::real_session_b_backlog` и пересчётом data-auditor 009). Для анализа обе строки игнорировать;
       - `disconnected` — соединение кончилось или не открылось. Здесь же выбранная пауза, в `detail` — `rule=<правило> <подробности>`. Причины (`reason`): `server_closed`, `idle_timeout` (нет ни одного кадра `--idle-timeout-secs`, по умолчанию 10 с), `block_idle`, `http_429`, `forbidden`, `http_error`, `net_error`;
       - причина `block_idle` (с задачи 012, 2026-10-01): кадры идут (ping, `confirmedSequenceNumberMessage`), но нет ни одного кадра с seq > 0 дольше `--block-idle-timeout-secs` (по умолчанию 30 с, 0 — выключено; отсчёт от начала сессии и от последнего кадра с блоком). recorder шлёт Close 1000 `"block idle timeout"`, пишет `client_close`, затем `disconnected block_idle` с `rule=transient` и `detail` вида `rule=transient no block (seq > 0) for 30s`. Пауза — всегда по лестнице `transient` (5 → 10 → … → 300 с, ±20 %), даже после сессии ≥ 30 с: при устойчивом залипании это не чаще ~11 подключений в час, а не каждые ~35 с. Сессия ≥ 10 мин (блоки шли до залипания) сбрасывает лестницу. Переподключение просит `last_seq + 1`, так что пропущенное закрывается бэклогом. Столбцы те же 11, новое только в `reason`/`detail`;
       - `startup_wait` — ожидание перед первым подключением после старта процесса. Причина `pending_pause` (остаток паузы, выбранной прошлым процессом, например `Retry-After` бана) или `min_connect_interval`. Ждём `max(остаток паузы, --min-connect-interval-secs − (now − конец прошлой сессии))`. С задачи 012 (2026-10-01) интервал считается **от конца** прошлой сессии, а не от `connected`: до 012 рестарт после долгой сессии подключался сразу. Конец — время последней строки любого типа после последнего `connected` (`client_close`, `disconnected`, `shutdown`, …); если строк после него нет (kill -9) — mtime самого нового часового файла данных. Более позднее из двух берётся и тогда, когда строки есть: с 009 через ~1 с после `connected` пишется `backlog`, и после kill -9 посреди долгой сессии последней строкой была бы она. mtime читается до ремонта торн-хвоста (ремонт меняет mtime) и до строк нового запуска. Нет ни одного `connected` в журнале — интервал не ждём. `detail`: `previous session ended <s>s ago (end=<log_row|data_mtime|connected>), min interval <N>s`; для `pending_pause` — `remaining pause from previous run, strikes=<k>`;
       - `torn_repair`, `gap_reconciled` (разрыв seq в данных, которого не было в `gaps.tsv`, дописан при старте);
       - `gaps_line_skipped` (с задачи 021, 2026-10-02) — строка `gaps.tsv`, пропущенная при старте recorder'а. `reason` = `broken` (битая строка, которая заканчивается `\n`) или `unterminated` (последняя строка без `\n`); остальные числовые столбцы `-`; `detail` = `gaps.tsv line <N>: <причина>: "<строка, escape_debug, до 200 символов>"`. За один старт — не больше 20 таких строк, остальные сводятся в одну строку `reason` = `more`, `detail` = `gaps.tsv: <K> more skipped lines not listed (<N> skipped in total)`. Повторяется при каждом старте, пока строки в файле (≤ 21 строка журнала за старт). Байты не UTF-8 в `gaps.tsv` (с задачи 025, 2026-10-02): файл читается с заменой битых последовательностей на U+FFFD и одним WARN в journal; строка, у которой они попали в `from`/`to`, становится `broken`, а байты в `recv_ns` на диапазон не влияют. До 025 такой файл давал выход 1 при каждом старте (crash-loop под systemd). Другие ошибки чтения (права, IO) — по-прежнему выход 1. Пауза прошлого запуска (`disconnected`) и конец прошлой сессии читаются из журнала до того, как пишется любая стартовая строка (исправление Б1 аудита 021: сотни таких строк вытесняли `disconnected 403` из читаемых 64 КиБ хвоста, и recorder подключался во время бана). Recorder при этом пишет дальше, а enricher `--gaps` на битой строке падает, так что её нужно исправить руками. healthcheck и `feed_audit.py` это событие не читают;
       - `shutdown` — остановка процесса. `reason`: `SIGINT`/`SIGTERM` или `writer_error` (с задачи 012: фатальная ошибка writer'а — диск, fsync; текст ошибки в `detail`). При `writer_error` recorder шлёт Close 1000 `"recorder writer error"`, ждёт ответ ≤ 2 с, пишет `client_close` и выходит с кодом **2**; до 012 выходил сразу, без Close. Если writer упал на финальном commit уже после сигнала, пишется отдельное событие `writer_error` с `reason=final_commit`, код выхода тоже 2. Коды выхода recorder: 0 — остановка по сигналу; 2 — ошибка writer'а; 1 — ошибка до начала работы (например, нельзя создать `--out-dir`);
       - `client_close` — итог Close 1000, который отправил recorder: `server_replied`, `no_reply`, `stream_ended` или `send_failed`. До 009 Close отправлялся только при остановке. С 009 он отправляется при любом обрыве по инициативе клиента: остановка, idle-таймаут, пропажа writer; с 012 ещё `block_idle` и фатальная ошибка writer'а. Причина Close (`"recorder shutdown"`, `"idle timeout"`, `"block idle timeout"`, `"recorder writer error"`, `"recorder writer gone"`) записана в `detail`. При idle-таймауте и `block_idle` строка идёт перед `disconnected`. При остановке (SIGINT/SIGTERM) и фатальной ошибке writer'а строки `disconnected` нет, порядок: `shutdown` → `client_close` → выход (проверено по `data/feed-test-009/connections.tsv` и `main.rs`, 2026-10-01; с задачи 021 этот код в `crates/recorder/src/app.rs`);
     - `_torn/`: оборванные хвосты после аварийного завершения. Это не сырьё для загрузки, только для разбора.
2. **Сырые блоки**: `data/blocks/blocks-<from>-<to>.jsonl.zst` — `{"number", "block"(full txs), "receipts"}`. Неизменяем.
   - Рядом `data/blocks/filled.tsv`: `from \t to \t file_name \t filled_unix_s`, одна строка на готовый файл режима `blocks`. Строка дописывается только после fsync и rename файла, так что состояние не опережает данные. По нему `enricher --gaps` пропускает уже закрытые диапазоны.
   - `enricher --gaps` (с задачи 012, 2026-10-01): последняя строка `gaps.tsv` без `\n` (recorder как раз её дописывает) пропускается с WARN `ignoring unterminated last line of gaps file`, следующий прогон её подхватит. Битая строка, которая заканчивается `\n`, по-прежнему ошибка.
   - Коды выхода enricher: 0 — готово; **75** (`EX_TEMPFAIL`, с задачи 012) — исчерпан `--max-calls`: готовые файлы уже в `filled.tsv`, недописанный `*.partial` удалён, следующий прогон продолжит (в systemd — `SuccessExitStatus=75`); 130 — прерван сигналом; 1 — любая другая ошибка.
   - Файлы пишутся атомарно: `*.partial` → fsync → rename. Файл `*.partial` всегда неполный, его нельзя загружать; при следующем запуске enricher его удаляет.
2a. **Сырые логи** (задача 003): `data/logs/logs-<from>-<to>.jsonl.zst`, получены через `eth_getLogs` с фильтром по topic0. Строка 1 — `{"meta":{"format":"hood-logs-v1","mode":"logs","topic0_any_of":[…],"not_full_blocks":true,…}}`. Далее по строке на каждый блок диапазона, по порядку, пустые тоже: `{"number":N,"logs":[<объекты eth_getLogs как есть>]}`. **Откатившихся транзакций здесь нет** (у них нет логов), нет газа и статуса. Это не замена `blocks`. Неизменяем.
3. **ClickHouse `hood.*`**: `blocks`, `txs`, `logs` — прямая загрузка сырья; `swaps`, `tokens`, `wallets`, `funding_edges`, `labels` — производные, пересобираемые из сырья.

## Соглашения

- Адреса: нижний регистр, `0x`-префикс, 42 символа. Хэши: нижний регистр, 66 символов.
- uint256/int256 храним строкой (`*_raw`) + нормализованный `Float64` рядом. Float только для аналитики, не для сверок.
- `quote_amount`, `price`, `fee_quote` — в единицах котируемого актива (ETH, USDG…), с учётом его decimals. Перевод в USD — отдельным шагом по цене на момент блока, никогда не «по сегодняшнему курсу».
- `side` — с точки зрения трейдера относительно токена: `buy` = трейдер получил токен.
- `trader` = подписант транзакции (`tx.from`), `router` = `tx.to`. Реальный бенефициар может отличаться (получатель в событии, контракт бота) — это отдельная колонка/таблица, когда понадобится.
- `feed_recv_ns` есть только у блоков, пришедших через recorder; у дозалитых из RPC — NULL. Любой анализ задержек фильтрует по NOT NULL.
- Метки (`labels`) всегда с `source` (какая эвристика) и `confidence`. Ручные метки — `source='manual'`. `source` входит в ключ (004): метки разных эвристик не схлопываются.

## L1-сообщения фида

Каждое сообщение фида — один L2-блок (`sequenceNumber` = номер блока). Вид — `header.kind`. Отложенные сообщения (из L1 inbox, kind ≠ 3) идут по одному на блок; у них `header.requestId` — сквозной номер отложенного сообщения, `delayedMessagesRead` растёт на 1, `header.blockNumber`/`header.timestamp` — L1-блок и время попадания в inbox (на 400–780 с раньше блока, не время блока). Источник и проверка — `chain-facts.md`, «L1-сообщения фида» (задача 014: Nitro v3.11.4 + 2 ч сырья + 16 вызовов RPC, 2026-10-01).

Во всех блоках tx с индексом 0 — `0x6a` StartBlock (`from`/`to` = `0x…0a4b05`, селектор `0x6bf6a42d`); в таблице она не повторяется. `miner` блока = `header.sender`, `nonce` блока = `delayedMessagesRead`.

| kind | Смысл (Nitro) | Частота, 01.10 09:57–12:00Z | tx в L2-блоке после StartBlock | Что брать декодерам |
|---|---|---|---|---|

Для графа финансирования (`funding_edges`): вход денег с L1 — это `0x64` (kind 12, kind 7) и `0x68` с `value` > 0 (kind 9). Они не видны в `logs` и не видны по `tx.from` как подпись пользователя: `from` — alias L1-адреса, unalias = вычесть `0x1111000000000000000000000000000000001111` mod 2^160. Мосты, которые платят на L2 из своего пула, создают обычный L2-перевод; это другой источник ребра (метка моста), не L1-сообщение.

Не видны ни в `value`, ни в логах (data-auditor 014, З3): возврат излишка `maxSubmissionFee` на `feeRefundAddr` у kind 9 (`tx_processor.go` L376-382) и перенаправление средств по onchain-фильтру (`0x64`/`0x69` → FilteredFundsRecipient). Суммы обычно малые. Декодер входов (задача 017) не делает из них строки, а считает как «не учтено» (см. ниже).

**Декодер входов с L1 (задача 017, `crates/decoders/src/l1_inflows/`, миграции `sql/002_funding_edges_l1.sql`, `sql/003_funding_edges_key.sql`).** Вход — строка `blocks-*.jsonl.zst`. Ключ — тип tx, а не `header.kind`: поэтому учитываются и ручные redeem `0x68` в обычных блоках, а kind 7 — по `0x64`. Строки `funding_edges`:
- `l1_eth`: `0x64` со `status=1` (to, value, `l1_request_id`) и `0x68` со `status=1`, `value` > 0, без `DepositFinalized` от `tx.to` (`retryTo`, value, `ticket_id`). `from_addr` = unalias(`tx.from`) — это **L1-адрес** (Ethereum), а не L2-аккаунт; для EOA он совпадает с адресом на L2.
- `l1_token`: `0x68` со `status=1`, в логах которого `DepositFinalized` испущен самим `tx.to` (шлюзом). `to_addr`/`value_wei` (сырые единицы токена) берутся из события, `from_addr` = `DepositFinalized.from` (депозитор на L1), `token` — эмиттер совпадающего `Transfer(шлюз|0x0 → to, amount)`. ETH-строки для шлюза нет. `gateway_status` — статус шлюза в реестре, который передаётся декодеру. Встроены только `verified` из `contracts.md` (сейчас L2 WETH gateway → L2 WETH). `none` = шлюза нет в реестре; такие строки по умолчанию отбрасывать.
- `0x69` строк не даёт никогда, иначе был бы двойной счёт с `0x68`.
- «Не учтено» — запись `UnaccountedFlow` и счётчик, в `funding_edges` не попадает:
  - `submit_fee_refund` — возврат этапа `0x69` на `FeeRefundAddr`, ровно `depositValue − retryValue − maxRefund` (по коду Nitro, сверено на 6 блоках, см. `chain-facts.md`);
  - `submit_no_redeem_upper_bound` — `0x69` без своего `0x68` в блоке, верхняя граница `depositValue − retryValue`;
  - `redeem_refund_upper_bound` — возвраты этапа `0x68` на `refundTo`, верхняя граница `maxRefund`;
  - `deposit_not_succeeded` — `0x64` со `status≠1` (onchain-фильтр → FilteredFundsRecipient; по коду, не наблюдали);
  - `submit_not_succeeded` — `0x69` со `status≠1`;
  - `retry_failed` — `0x68` со `status=0` и `value` > 0 (деньги вернулись в эскроу);
  - `gateway_eth_unexplained` — `tx.value` шлюзовой `0x68` ≠ сумме токенов;
  - `retry_no_to`;
  - `unregistered_gateway_eth` (задача 027, ревью 017 З2) — `0x68` со `status=1` и `value` > 0 в контракт **вне реестра**, который испустил `DepositFinalized`, и сумма токенов = `tx.value`. Строки `l1_token` (`gateway_status = none`) по умолчанию отбрасываются, а `l1_eth` нет; если контракт не настоящий шлюз, ETH остался у `to`. Запись: `addr` = `to`, сумма = `tx.value`. На данных не наблюдалось (проверено 2026-10-03: 0 на 2 712 блоках `data/blocks` + `data/samples`); на фикстуре 017 срабатывает только с `--no-builtin` (блок 77312169).

  Отмену и истечение тикета (эскроу → `beneficiary`) декодер не видит совсем: для этого нужна трассировка или событие ArbRetryableTx `Canceled`.
- Ключ — `ORDER BY (to_addr, block_number, tx_index, kind, log_index)` (миграция 003, см. «Схема и миграции»): строки `l1_eth` пишутся с `log_index` = 4294967295 (уровень tx), строки `l1_token` — с индексом своего `DepositFinalized`, поэтому несколько депозитов одному получателю в одной tx не схлопываются.

## Чего нет в данных (и как это учитывать)

- Внутренние переводы ETH между контрактами: нужны трассировки. Без них граф финансирования неполный — в отчётах указывать.
- Транзакции, отклонённые секвенсором или не дошедшие до него: не видны никогда. «Доля успешных» считается только среди включённых в блок.
