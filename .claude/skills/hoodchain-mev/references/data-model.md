# Модель данных

Схема: `sql/001_schema.sql`. Изменения схемы — новым файлом миграции (`002_…sql`), не правкой старого.

## Слои

1. **Сырой фид**: `data/feed/YYYY/MM/DD/feed-YYYYMMDD-HH.tsv.zst`. Строка: `recv_unix_ns \t seq_first \t seq_last \t <JSON конверта как есть>`. Неизменяем. После перезапуска recorder дописывает новый zstd-фрейм в тот же часовой файл: читать с поддержкой нескольких фреймов (`zstd -dc` умеет; в Python `stream_reader(..., read_across_frames=True)`).
   - С задачи 002, 2026-09-30, recorder закрывает zstd-фрейм не реже раза в 60 с, поэтому фреймов в часовом файле много.
   - Строки с `seq_first = seq_last = 0` — обычное дело, и при разборе их нужно пропускать или разбирать отдельно:
     - конверты без `messages`, например `{"version":1,"confirmedSequenceNumberMessage":{"sequenceNumber":N}}`;
     - нетекстовые фреймы (ping и др.) в обёртке recorder: `{"recorderFrame":{"opcode":"ping","payloadBase64":"…"}}`. Ключа `recorderFrame` в фиде не бывает;
     - текстовый фрейм, который не парсится как JSON: с задачи 008 (2026-09-30) — в той же обёртке с `"opcode":"text"`, байты текста в `payloadBase64` без изменений. До 008 такой текст писался как есть, с вырезанными `\n`/`\r` (на записанных данных таких строк 0);
     - валидный JSON, который не похож на конверт (например, `messages` не массив), — как есть.
   - Столбец JSON всегда валидный JSON. Из него удаляются только `\n`, `\r` и `\t`. В валидном JSON эти символы могут быть лишь незначащими пробелами между токенами: внутри строк управляющие символы запрещены (RFC 8259, разд. 7). Поэтому значение не меняется, а в строке всегда ровно 4 TSV-поля. `\t` удаляется с задачи 009 (2026-10-01, замечание Р2 аудита 008); раньше он оставался, но на данных 001–002 таких строк 0 из 11 983. Делить строку всё равно надёжнее не более 3 раз (`split('\t', 3)`).
   - **Повторы seq в сырье возможны, дедупликация — обязанность разбора и загрузчика.** Recorder пропускает конверт целиком (счётчик `dup_skipped`), только если все его seq ≤ уже записанного. Конверт, который частично перекрывает записанное (`seq_first ≤ last_seq < seq_max`), пишется целиком, как пришёл: сырьё не режется. Поэтому при разборе ключ блока — `sequenceNumber`; какое вхождение брать при повторе, решает загрузчик (правило описать в его задаче). Расхождение `blockHash` у повторов — ошибка данных, о ней надо сообщать. На данных 001–002 таких конвертов 0: в каждом конверте было ровно 1 сообщение. `feed-audit` считает повтор seq ошибкой (FAIL), так что такой случай будет виден.
   - Рядом с сырьём лежат:
     - `gaps.tsv`: `from \t to \t recv_ns`;
     - `last_seq.txt`: последний seq, уже записанный на диск (fsync);
     - `connections.tsv`: события соединения и паузы, первая строка — заголовок. Столбцы: `ts_utc, ts_unix_ns, event, reason, http_status, retry_after, pause_s, session_s, envelopes, strikes, detail`. У строк первого запуска 002 нет столбца `strikes` (10 столбцов вместо 11). События:
       - `connected` — апгрейд прошёл. С задачи 009 в `detail` после URL идут `requested=<N|->` и `mode=<header|no_data|disabled>`. `header` — отправлены `Arbitrum-Feed-Client-Version: 2` и `Arbitrum-Requested-Sequence-Number: N`, где N = last_seq + 1. last_seq берётся из памяти процесса, а при старте — из данных (`recover`), не из `last_seq.txt`. `no_data` — данных нет, заголовки не отправлялись. `disabled` — задан флаг `--no-requested-seq`;
       - `backlog` (с задачи 009) — статистика бэклога соединения. Бэклог — кадры с seq до первого «живого» кадра, то есть кадра, у которого самое новое `header.timestamp` среди сообщений kind 3 отстаёт от времени приёма меньше чем на 2 с. Сам живой кадр в бэклог не входит. Правило зависит от часов (NTP); kind 9/13 не учитываются, у них время L1-inbox. Правило «до первой паузы > 30 мс» не годится: в живой проверке 009 бэклог шёл с паузами до 99 мс. Строка пишется один раз: `reason=done`, когда пришёл живой кадр, или `session_ended`, если соединение кончилось раньше. `envelopes` — число блоков бэклога, `session_s` — время от первого кадра до живого. В `detail`:
         - `requested`, `last_seq_before`, `first_seq` (первый полученный seq);
         - `first_minus_requested`: 0 — сервер начал с запрошенного; > 0 — начал позже, тогда в `gaps.tsv` будет дыра;
         - `first_lag_ms`, `backlog_blocks`, `backlog_end_seq`, `live_seq`, `live_lag_ms`, `live_after_ms`;
         - `stale_frames` — кадры, где все seq ≤ last_seq; их пропускает writer, это `dup_skipped`;
         - `complete`.

         Без заголовка первый кадр уже живой, `backlog_blocks` = 0. Статистика пишется отдельной строкой, а не столбцами `connected`, потому что `connected` должен попасть на диск сразу после апгрейда: по нему считается `--min-connect-interval-secs`. В `data/feed-test-009` строка `backlog` сессии B записана ещё по старому правилу (паузы > 30 мс) и показывает 6 блоков; по новому правилу там 621 блок (проверено тестом `resume::tests::real_session_b_backlog` на этих данных);
       - `disconnected` — соединение кончилось или не открылось. Здесь же выбранная пауза;
       - `startup_wait` (причина `pending_pause` или `min_connect_interval`), `torn_repair`, `gap_reconciled` (разрыв seq в данных, которого не было в `gaps.tsv`, дописан при старте), `shutdown`;
       - `client_close` — итог Close 1000, который отправил recorder: `server_replied`, `no_reply`, `stream_ended` или `send_failed`. До 009 Close отправлялся только при остановке. С 009 он отправляется при любом обрыве по инициативе клиента: остановка, idle-таймаут, пропажа writer. Причина Close (`"recorder shutdown"`, `"idle timeout"`, `"recorder writer gone"`) записана в `detail`. Строка идёт перед `disconnected`, если тот пишется; при остановке (SIGINT/SIGTERM) строки `disconnected` нет — за `client_close` следует `shutdown`;
     - `_torn/`: оборванные хвосты после аварийного завершения. Это не сырьё для загрузки, только для разбора.
2. **Сырые блоки**: `data/blocks/blocks-<from>-<to>.jsonl.zst` — `{"number", "block"(full txs), "receipts"}`. Неизменяем.
   - Рядом `data/blocks/filled.tsv`: `from \t to \t file_name \t filled_unix_s`, одна строка на готовый файл режима `blocks`. Строка дописывается только после fsync и rename файла, так что состояние не опережает данные. По нему `enricher --gaps` пропускает уже закрытые диапазоны.
   - Файлы пишутся атомарно: `*.partial` → fsync → rename. Файл `*.partial` всегда неполный, его нельзя загружать; при следующем запуске enricher его удаляет.
2a. **Сырые логи** (задача 003): `data/logs/logs-<from>-<to>.jsonl.zst`, получены через `eth_getLogs` с фильтром по topic0. Строка 1 — `{"meta":{"format":"hood-logs-v1","mode":"logs","topic0_any_of":[…],"not_full_blocks":true,…}}`. Далее по строке на каждый блок диапазона, по порядку, пустые тоже: `{"number":N,"logs":[<объекты eth_getLogs как есть>]}`. **Откатившихся транзакций здесь нет** (у них нет логов), нет газа и статуса. Это не замена `blocks`. Неизменяем.
3. **ClickHouse `hood.*`**: `blocks`, `txs`, `logs` — прямая загрузка сырья; `swaps`, `tokens`, `wallets`, `funding_edges`, `labels` — производные, пересобираемые из сырья.

## Соглашения

- Адреса: нижний регистр, `0x`-префикс, 42 символа. Хэши: нижний регистр, 66 символов.
- uint256/int256 храним строкой (`*_raw`) + нормализованный `Float64` рядом. Float только для аналитики, не для сверок.
- `quote_amount`, `price`, `fee_quote` — в единицах котируемого актива (ETH, USDG…), с учётом его decimals. Перевод в USD — отдельным шагом по цене на момент блока, никогда не «по сегодняшнему курсу».
- `side` — с точки зрения трейдера относительно токена: `buy` = трейдер получил токен.
- `trader` = подписант транзакции (`tx.from`), `router` = `tx.to`. Реальный бенефициар может отличаться (получатель в событии, контракт бота) — это отдельная колонка/таблица, когда понадобится.
- `feed_recv_ns` есть только у блоков, пришедших через recorder; у дозалитых из RPC — NULL. Любой анализ задержек фильтрует по NOT NULL.
- Метки (`labels`) всегда с `source` (какая эвристика) и `confidence`. Ручные метки — `source='manual'`.

## Чего нет в данных (и как это учитывать)

- Внутренние переводы ETH между контрактами: нужны трассировки. Без них граф финансирования неполный — в отчётах указывать.
- Транзакции, отклонённые секвенсором или не дошедшие до него: не видны никогда. «Доля успешных» считается только среди включённых в блок.
