## Блокирующее

**Б1. Ошибка запроса `apply-unless` превращается в `skipped` и запись в журнале** (`sql/apply.sh:183`).
- Что не так:
  ```bash
  if [ -n "$guard" ] && [ "$(printf '%s' "$guard" | ch)" != "0" ]; then
      outcome=skipped
  ```
  Подстановка `$(…)` внутри условия `[ ]` не подпадает под `set -e`. Если `ch` упал (сервер перезапускается, таймаут, опечатка в guard, неверная БД), подстановка вернёт пустую строку или тело ошибки ClickHouse (`--fail-with-body` пишет тело в stdout). Это `!= "0"`, поэтому миграция помечается `skipped`, строка уходит в `hood.schema_migrations`, печатается `skipped: 003`, итог `changes: 1`, код выхода 0. Все следующие прогоны считают её применённой (`already applied`).
- Проверено 2026-10-02: тот же фрагмент в `bash 3.2.57` с `set -euo pipefail` и `ch`, который возвращает 22 и печатает `Code: 60. DB::Exception…`, даёт `outcome=skipped`, скрипт продолжается, exit 0 (скрипт в scratchpad).
- Почему важно здесь: guard есть ровно у миграции, ради которой задача заведена. Ложный `skipped` у 003 оставляет старый ключ `(to_addr, block_number, tx_index)`, и после появления загрузчика рёбра снова молча схлопываются (В1). Журнал при этом утверждает обратное, а это единственный источник «что применено». По скиллу это «тихая порча» состояния схемы.
- Исправление:
  ```bash
  outcome=applied
  if [ -n "$guard" ]; then
      g=$(printf '%s' "$guard" | ch) || die "$name: apply-unless query failed: $g"
      [[ "$g" =~ ^[0-9]+$ ]] || die "$name: apply-unless must return one number, got: $g"
      [ "$g" = "0" ] || outcome=skipped
  fi
  if [ "$outcome" = applied ]; then
      dir="$TMP/$ver"; mkdir -p "$dir"
      …   # split + run, as now
  fi
  ```
  Проверка: временно испортить guard в копии 003 (несуществующая колонка) на одноразовом контейнере — ожидается `die`, без записи в журнал.
- Остальные вызовы `ch` в скрипте стоят в обычных присваиваниях (`have_log=…`, `recorded=…`, `:148`, `:166`) или в пайпе с `>/dev/null` — там `set -e`/`pipefail` срабатывают. Проверил по тексту, другой такой ловушки нет.

## Рекомендации

**Р1. Остаток `funding_edges_pre003` прячется за guard** (`003:28`, `:62-71`).
- Сценарий: строка попала в старую таблицу между первым `throwIf` и `RENAME` (сейчас некому, загрузчика нет). Второй `throwIf` срабатывает после второго `RENAME`: новая таблица уже на месте, старая сохранена как `funding_edges_pre003`, `apply.sh` падает, журнал не пишется. Это правильно и громко. Но следующий прогон видит новый ключ, guard даёт 1 → `skipped`, и `pre003` со строками остаётся навсегда без единого сообщения.
- Исправление (сохраняет идемпотентность):
  ```sql
  -- apply-unless: SELECT count() = 1 AND (SELECT count() FROM system.tables WHERE database = 'hood' AND name IN ('funding_edges_pre003', 'funding_edges_003')) = 0 FROM system.tables WHERE database = 'hood' AND name = 'funding_edges' AND sorting_key = 'to_addr, block_number, tx_index, kind, log_index'
  ```
  Тогда при остатке guard вернёт 0, файл пойдёт выполняться и упадёт на первом `throwIf` (новая таблица) или на `RENAME` — громко. Файл ещё не закоммичен и не применялся нигде, кроме локального тома: после правки sha256 изменится, локально придётся удалить запись 3 из журнала (или пересоздать том). Если не хочется трогать sha — описать сценарий в комментарии 003 рядом с инструкцией про прерванный RENAME.

**Р2. Ожидание сервера без таймаута соединения** (`apply.sh:129`).

## Что хорошо (не сломать при правках)

- Пароль не попадает в argv и `ps`: curl-конфиг из `printf` (builtin) через `-K <(…)`; `.env` читается построчно, не исполняется; окружение важнее `.env`.
