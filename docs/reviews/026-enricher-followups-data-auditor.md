## Замечания (не блокируют PASS)

**Н1. Сумма проверяется в конце кадра, а данные отдаются потоком.** `zstd -dc` пишет распакованные байты до сверки XXH64. `hoodlib.iter_block_lines` отдаёт строки по мере чтения и проверяет код возврата `zstd` только в конце: в 244 из 300 случаев порченые строки дошли до `json.loads` раньше, чем сработала сумма. `hourly_metrics.py` безопасен: он пишет во временный файл с rename, а при ошибке временный файл удаляется. Любой будущий **потоковый** потребитель (загрузчик в ClickHouse, декодеры по строкам) должен учитывать то же: либо `zstd -t` до загрузки, либо вставка, которая откатывается целиком при ненулевом коде `zstd`. Рекомендация для задачи загрузчика, к 026 не относится.

**Н2. Неточность в отчёте исполнителя.** В «Предполагается» сказано, что `hoodlib.py` читает через Python `zstandard`. На деле он вызывает CLI `zstd -dc` (`iter_block_lines`), поэтому отдельный модуль не нужен. Чтение новых файлов я проверил прогоном (п. 1). В `data-model.md` Python `zstandard` упомянут как один из возможных читателей. Это не ошибка, но в проекте сейчас его никто не использует.

**Н3. Старые файлы остаются без суммы.** Это 7 файлов локально в `data/blocks` и всё, что enricher записал на сервере до 026. Порча в них по-прежнему может пройти тихо (~80 % одиночных порч на моке). Перепаковка `zstd -dc | zstd -3 --check` формат строк не меняет. Решение — за Михаилом.

**Н4. `--mode logs` не проверяет план по бюджету.** `--mode logs --max-calls 1` → 75 на каждом запуске, 1 вызов (`eth_chainId`), без прогресса. Это тот же класс, что прежний З4, но для logs. Отказ обоснован в doc (окно адаптивное, число вызовов зависит от данных) и в systemd этот режим не запускается. Как минимум `--max-calls < 2` (chainId + одно окно) можно было бы отвергать сразу.

**Н5. (известно)** Комментарий в шапке `deploy/enricher-gaps.service` («4000 calls = 2000 blocks per run») неверен до решения Михаила по 4001/4201.

## Предполагается / не проверено

- Что `zstd` CLI на сервере тоже проверяет content checksum. Это стандартное поведение zstd ≥ 1.0, но проверял я только локально (`zstd` 1.5.7).
- Поведение на реальных данных провайдера: мок по структуре похож на настоящие блоки, но не тождествен. Сжатие не зависит от содержимого строк, поэтому вывод «распакованное = HEAD» на реальные данные переносится. Это вывод из кода (`include_checksum` — единственное изменение кодировщика), прогоном на реальном RPC не проверял.
- Стандартные пункты чек-листа data-auditor (сверка свопов, decimals, дубли ReplacingMergeTree, статусы) к задаче не относятся: декодеры и таблицы она не меняет. Применимые части покрыты пунктами 1 и 2: полнота (файлы и строки `filled.tsv` те же), порядок блоков (побайтовое совпадение распакованного), состояние не опережает данные.
