## 4. Знак v4 и его нормализация — PASS

**Данные (проверено 2026-10-02, `swaps_audit.py`).** Для каждой ненулевой суммы свопа я искал в том же чеке ERC-20 `Transfer` на ту же сумму в эмиттер или из него (пул для v3, PoolManager для v4). Исход классифицирован однозначно: «в», «из», «оба» (есть и та, и другая) или «нет».

| venue, сырой знак | в эмиттер | из эмиттера | оба | нет |
|---|---|---|---|---|
| v3, > 0 | **6 854** | 0 | 5 | 3 |
| v3, < 0 | 0 | **6 856** | 4 | 1 |
| v4, > 0 | 1 | **3 110** | 228 | 3 310 |
| v4, < 0 | **4 124** | 3 | 356 | 2 169 |

- **Только tx с одним свопом** (нет путаницы между ногами одной tx):
  - v3: 4 057 из 4 057 «> 0 → в пул», 4 057 из 4 057 «< 0 → из пула»;
  - v4: 1 720 «> 0 → из PoolManager» против 0 обратных, 1 828 «< 0 → в PoolManager» против 0 обратных.

  Противоречий 0.
- **4 «обратных» случая v4** (33969231 tx 14, 44813516 tx 10, 55603962 tx 4, 64635093 tx 6) разобраны вручную. Все в tx с 2+ свопами (круговые маршруты): сумма одной ноги случайно равна `Transfer` соседней ноги. Это не нарушение знака.
- **«Нет» у v4 — нативный ETH.** 4 096 таких сумм приходятся на `amount0` и 1 383 на `amount1`. В v4 нативный ETH (`address(0)`) всегда `currency0`. У 1 225 из 1 992 отрицательных `amount0` без `Transfer` `tx.value` ≥ суммы. Остаток объясняется зачётом внутри PoolManager (flash accounting, многоходовые маршруты).
- Цифры отчёта согласуются с моими: v3 6 859 = 6 854 + 5, v4 3 338 = 3 110 + 228, 229 = 1 + 228. Отчёт считал «оба» в обе стороны, поэтому его соотношение (3 338 : 229) выглядит хуже реального (3 110 : 1), см. З1.

**Семантика PoolManager (предполагается: по исходникам v4-core, которые я помню; в этой сессии не перечитывал, документацию не запрашивал).**
- `_swap` испускает `Swap(id, msg.sender, delta.amount0(), delta.amount1(), …)`, где `delta` — `BalanceDelta` из `Pool.swap`.
- Эта же дельта зачисляется вызывающему через `_accountPoolBalanceDelta(key, swapDelta, msg.sender)`: положительная — PoolManager должен вызывающему, отрицательная — вызывающий должен PoolManager.
- Значит, сырой знак v4 — сторона свопера, а `-delta` — сторона пула, как в v3. Нормализация `pool_side()` верна, данные выше подтверждают это без исключений.
- Переполнения нет: отрицание int128 в I256 безопасно.

## Замечания

- **З1. Цифры v4 в `chain-facts.md` и doc `PoolSwap` (низкая важность).**
  - Сейчас: «3 338 против 229», «4 480 против 359». Обе пары включают 228/356 неоднозначных совпадений («оба») в обе стороны.
  - Однозначные цифры: 3 110 против 1 и 4 124 против 3. В tx с одним свопом — 1 720 : 0 и 1 828 : 0.
  - Факт верен, но записан слабее, чем есть. Рекомендую уточнить при следующей правке. Не блокирует.
- **З2. Суммы v4 в пулах с хуками — не суммы трейдера (важно для `hood.swaps`, предполагается по коду v4-core).**
  - `Swap` испускается внутри `_swap`, то есть до `afterSwap`.
  - `beforeSwap` может изменить `amountToSwap` (`BeforeSwapDelta`), а `afterSwap` — вернуть `hookDelta`.
  - Для пулов с custom accounting (возможно, Pons v2 / pools.trade) событие показывает AMM-ногу, а не то, что трейдер заплатил и получил.
  - Знак нормализован верно, но цена и объём по таким пулам требуют учёта хуков. Это совпадает с пунктом «предполагается» в отчёте. До декодера `hood.swaps` нужно сверить суммы с `Transfer` и с сальдо по `pool_id` хуковых пулов.
- **З3. Нулевые суммы в сырье (для загрузчика `hood.swaps` и расчёта цены).**
  - 20 свопов с нулевой суммой:
    - v4 `[0, 0]` — 16, из них 14 с `liquidity = 0`, 7 в одном `pool_id` `0x4f1d3a2b…c556`;
    - v4 с одной ненулевой суммой ±1 (сырые `[-1, 0]` ×2 и `[0, -1]` ×1) — 3;
    - v3 `[0, 3709]` — 1 (47247730 tx 2 log 13).
  - Кроме того, `fee_pips = 0` у 2 201 из 6 668 свопов v4 (33%).
  - Декодер передаёт эти значения как есть, и это правильно. Но цена `amount1/amount0` на них делится на 0. Нужно правило фильтрации или флаг в задаче загрузчика.
- **З4. L1-путь на данных не нагружен.** В 2 712 блоках 0 L1-сообщений. Побайтная идентичность L1-строк доказана только на 4 блоках фикстуры (и на юнит-тестах с синтетикой). Новые ветки (`token_sum_overflow`, `Agg.overflowed`, `\N` у `addr`) на реальных данных не встречались. Для фазы 1b нужна выборка с L1-сообщениями за длинное окно (вопрос из ревью 017 остаётся).
- **З5. З2 из ревью 017** (контракт вне реестра испускает `DepositFinalized` и забирает ETH-строку) не закрыт, вне объёма 022. Остаётся открытым до задачи загрузчика `funding_edges`.
