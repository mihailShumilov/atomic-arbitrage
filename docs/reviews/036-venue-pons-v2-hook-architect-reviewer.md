## Важное

**В1. [crates/decoders/src/pools.rs:186–190 (`insert`) и :229–235 (`allow_v4_hook`)] Инвариант `pons_v2_hook` не привязан к хуку Pons.**

Что не так:
- Проверка в `insert` — `e.venue != PonsV2Hook || (v4 && e.hooks != Some(ZERO))`. Она пропускает v4-пул с `hooks = None` (в TSV `-`, «неизвестно») и с **любым чужим** хуком.
- `allow_v4_hook` отсекает только `uni_v3`/`uni_v4`/`other`. Поэтому хук можно разрешить с площадкой `pons_v1` или `pons_v2_curve`, хотя это кривые лаунчпада, а не v4-хуки. Можно и разрешить чужой адрес с `pons_v2_hook`.

Проверено 2026-10-05: временный крейт в scratchpad с зависимостью `decoders` по пути, после проверки удалён. Результаты:

```
pons_v2_hook … hooks=-                       -> Ok (accepted as pons_v2_hook)
pons_v2_hook … hooks=0x4e34…a544 (Doppler)   -> Ok (accepted as pons_v2_hook)
allow_v4_hook(Doppler, PonsV1, observed)     -> Ok(())
```

Почему это важно здесь:
- Смысл задачи в том, что аналитика отличает Pons-пулы по `venue`, а не по списку адресов (решение Михаила).
- Сейчас строка реестра, написанная руками или другим скриптом, может тихо пометить пул Doppler как `pons_v2_hook`. Тест этого не поймает, data-auditor увидит только по косвенным признакам.
- На текущих входах порчи нет: в `pools-035.tsv` такие пулы записаны как `other`.
- Но исполнитель сам спрашивает, не переписать ли этот файл на `pons_v2_hook` (его вопрос 2). Тогда эта проверка становится единственной защитой.

Исправление. Правило должно быть статичным и не зависеть от порядка регистрации, тогда `parse_tsv` из пустого реестра тоже работает:

```rust
/// `pons_v2_hook` is by definition the venue of pools of the Pons v2 meme hook (task 036).
fn venue_fits_hooks(venue: Venue, hooks: Option<Address>) -> bool {
    venue != Venue::PonsV2Hook || hooks == Some(PONS_V2_MEME_HOOK)
}
```

- В `insert`: `ensure!(v4 || e.venue != Venue::PonsV2Hook, …)` заменить на `ensure!(venue_fits_hooks(e.venue, e.hooks), "pool {:?}: venue pons_v2_hook needs hooks {PONS_V2_MEME_HOOK:#x}", e.pool)`. Для v3 условие выполняется автоматически: у v3 `hooks = None`.
- В `allow_v4_hook`:
  - вместо чёрного списка — белый: `ensure!(matches!(venue, Venue::PonsV2Hook | Venue::PoolsTrade), …)`; pools.trade оставлен на случай, если его хук подтвердится (`todo` в data-model.md);
  - плюс `ensure!(venue_fits_hooks(venue, Some(hook)), …)`.
- Тесты в `allow_v4_hook_checks`:
  - `insert` `pons_v2_hook` с `hooks = None` и с чужим хуком — ошибка;
  - `allow_v4_hook(h, PonsV1)` — ошибка;
  - `allow_v4_hook(doppler, PonsV2Hook)` — ошибка.
- Если Михаил когда-нибудь признает старую версию хука Pons (`0x5738…2044`, предупреждение в contracts.md) площадкой `pons_v2_hook`, правило расширяется до списка адресов из `addresses.rs`. Это отдельное решение, а не параметр CLI.

Поведение и формат данных исправление не меняет: на входах 035 у пулов этого хука везде `other` или правильный хук, проверено исполнителем — 1 242 строки, все с `hooks = 0xe5e7…e044`.

## Рекомендации

**Р1. [crates/decoders/src/rows.rs:506–509, `current_table`] Поиск ALTER зависит от вида строки.**
- `l.contains("ALTER TABLE hood.swaps ")` не найдёт `ALTER TABLE hood.swaps` в конце строки, если `MODIFY` перенесён на следующую строку: там нет пробела после имени. Не найдёт и `ALTER TABLE IF EXISTS hood.swaps`. Такой ALTER тест молча пропустит, и сверка enum с SQL станет ложно-зелёной.
- Исправление: искать по токенам. Любая строка, где есть `ALTER` и `TABLE` и токен равен `hood.<table>`, без однострочной формы `ALTER TABLE hood.<t> MODIFY COLUMN …` → `panic!("unsupported ALTER … update this test")`:

```rust
let mentions = |l: &str| l.contains("ALTER") && l.split_whitespace().any(|t| t == name);
```

- Сам подход (накладывать `MODIFY COLUMN` на тело последнего `CREATE`, любой другой ALTER — падение) правильный и простой. Отдельный парсер SQL не нужен.

**Р2. [sql/005_venue_pons_v2_hook.sql:17, 23–24, 29, 31, 36] Литерал целевого Enum8 повторён 5 раз.**
- В SQL без переменных этого не избежать: `apply-unless` должен помещаться в одну строку.
- Риск небольшой и громкий: опечатка в проверке после ALTER или в предварительной проверке роняет миграцию, опечатка в `apply-unless` только отключает пропуск (файл идемпотентен).
- Предлагаю одну строку в шапке: «the Rust test checks only the ALTER lines; the throwIf/apply-unless literals must equal them». Это одна строка комментария, файл ещё не применён на сервере.
- Оговорка: на локальном томе исполнителя 005 уже `applied`, его sha256 записан в журнал. Если правку внести, на локальном томе нужно один раз удалить строку 005 из `hood.schema_migrations` и снова запустить `apply.sh`, получится `skipped`. Если это неудобно, оставить как есть.

## Ответ на вопрос исполнителя: заменить встроенный хук флагом `--v4-hook`?

**Нет, встроенный хук оставить.** Обоснование:

1. **Хук — это определение площадки, а не настройка.**
   - Значение `pons_v2_hook` в Enum8 схемы и вариант `Venue::PonsV2Hook` по определению означают пулы этого хука (решение Михаила).
   - Если связь вынести во флаг, результат зависит от вызова. Без флага те же блоки дают 1 242 строки `other` вместо `pons_v2_hook`, и в `hood.swaps` одни и те же данные получат разную разметку в зависимости от того, кто и как запускал.
   - Будущий загрузчик строк `hood.swaps` тоже должен был бы помнить этот флаг. Встроенная константа — один источник правды для примера, загрузчика и тестов.
2. **Правило реестра соблюдено.**
   - Адрес в `addresses.rs` со статусом `verified` (contracts.md, Михаил, 2026-10-05), с источником в doc-комментарии; включён в `VERIFIED` и в тест модуля.
   - Это тот же образец, что `L2_WETH` и `TokenRegistry::builtin()`.
3. **PoolManager передаётся параметром по историческим причинам.**
   - Механизм `--v4-manager` появился, когда PoolManager был `observed` (задачи 031/033). С 2026-10-05 он тоже `verified`.
   - Если добиваться единообразия, то в обратную сторону: встроить PoolManager (`addresses.rs` + `PoolRegistry::builtin()`), а не выносить хук во флаг.
   - Но это меняет поведение запуска по умолчанию: пример начнёт регистрировать пулы из `Initialize` без флагов. Кроме того, PoolManager — фильтр эмиттеров, то есть граница доверия, и явный параметр там тоже оправдан. Поэтому это отдельная маленькая задача по решению Cowork или Михаила, не 036.
4. **Флаги можно оставить.** `--no-builtin-hooks` нужен для сравнения «до/после»; исполнитель им воспользовался, это колонка таблицы в отчёте. `--v4-hook` пригодится для `observed`-хуков в исследованиях. После В1 он не сможет выдать `pons_v2_hook` чужому адресу.

На вопрос 2 исполнителя (переписать `venue` в `pools-035.tsv`): архитектурно это не нужно, `other` повышается кодом. Если переписывать, то только после В1, иначе строку с ошибкой в этом файле ничто не поймает.
