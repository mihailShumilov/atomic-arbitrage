## Рекомендации

**Р1. Для будущих миграций пересоздания (005+): один общий pre-flight `throwIf` в начале файла.** `004:40-265`.
- Сейчас проверка пустоты идёт по каждой таблице прямо перед её пересозданием. Если, например, `labels` непуста, к моменту отказа `txs`…`wallets` уже пересозданы: исполнитель так и проверил (`--to 3` + строка в `labels`). Данные при этом целы, потому что пересоздаются только пустые таблицы, а повтор доводит файл до конца. Но схема остаётся смешанной (часть таблиц 001, часть 004), а в журнале записи нет. Это корректно, но читать такое состояние неудобно.
- Исправление (только в шаблон следующих миграций; 004 уже в журнале локального тома, её sha трогать не надо): первым стейтментом одна проверка по всем таблицам файла, а потабличные `throwIf` оставить как защиту от гонки:
  ```sql
  SELECT throwIf(
      (SELECT sum(total_rows) FROM system.tables WHERE database = 'hood' AND name IN ('txs', 'logs', ...)) > 0
      OR (SELECT count() FROM system.detached_parts WHERE database = 'hood' AND table IN ('txs', 'logs', ...)) > 0,
      'NNN: some of the recreated tables are not empty: nothing changed'
  );
  ```
  `total_rows` у MergeTree точный; если не хочется на него полагаться, можно сложить `(SELECT count() FROM hood.<t>)` по таблицам. Пусть это будет одной строкой в `data-model.md` («пересоздание нескольких таблиц: сначала общий отказ, потом по таблице»), без генератора и без шаблонизатора.

**Р2. Запрет DDL срабатывает только для файлов, которые реально выполняются.** `apply.sh:197-206`.
- Проверка стоит внутри `if [ "$outcome" = applied ]`. Поэтому `--dry-run` запрещённый стейтмент не показывает. Файл, который на этом томе пропущен по `apply-unless`, тоже не проверяется, а на свежем томе тот же файл пойдёт выполняться. Отказ всё равно случится до первого стейтмента, то есть безопасно, но позже, чем мог бы.
- Исправление (поведение для корректных файлов не меняется). Разбор и проверку перенести сразу за проверку журнала (после `continue` для `recorded`), до ветки `DRY_RUN` и до `apply-unless`:
  ```bash
  dir="$TMP/$ver"; mkdir -p "$dir"
  split_sql "$f" "$dir" || die "$name: cannot split statements"
  check_banned "$name" "$dir"        # тот же цикл tr|grep, вынесенный в функцию
  ```
  В ветке `applied` останется только цикл отправки. В тест добавить два случая: запрещённый стейтмент + `--dry-run` → exit 1; запрещённый стейтмент + `one_guard` → exit 1, в журнале пусто. Цена — около 6 строк.

**Р3. Хвостовой пробел в ожидаемом выводе лексер-теста.** `test_apply.sh:94` (`INSERT INTO t VALUES (1), ` с пробелом в конце).
- `git diff --check` на нём ругается. Любой редактор с «trim trailing whitespace» уберёт пробел, и тест упадёт без видимой причины.
- Исправление: во входе убрать пробел перед комментарием, `INSERT INTO t VALUES (1),-- tail; comment` (строка 86). Тогда ожидаемая строка 94 — `INSERT INTO t VALUES (1),` без пробела. Лексер проверяется так же.

**Р4. Один и тот же Enum8 `venue` в двух таблицах, тестом они не связаны.** `004:120` и `004:157`.
- Решение «одно понятие — один тип» верное (`schema-types-enum`: площадки — малое конечное множество, ошибка на вставке ловит опечатки). Но значения теперь записаны дважды, и при следующем `MODIFY COLUMN` одну из таблиц легко забыть. Rust-перечисления `Venue` пока нет: декодеры свопов ещё TODO.
- Исправление — когда появится `Venue` в `crates/decoders`: тест по образцу `enum8_in_sql_equals_rust_enums` должен проверять **оба** определения (`swaps.venue` и `tokens.venue`), а не последнее вхождение `venue`, как делает `last_enum8`. Сейчас ничего не делать; достаточно пометки в задаче декодера свопов.

**Р5. Запрет шире, чем таблицы.** `apply.sh:203`: `CREATE OR REPLACE ` запрещает и `VIEW`/`DICTIONARY`/`FUNCTION`, а `REPLACE DICTIONARY` не ловит.
- Для этого репозитория так даже лучше: представлений нет, а замена через временный `.sql` и `metadata_dropped`, скорее всего, ломается так же (предполагается, не проверялось). Менять регэксп не нужно. Можно добавить в шапку `apply.sh:28` слово «any object», чтобы это не выглядело ложным срабатыванием, когда появятся VIEW.

**Р6. Кардинальность `selector` проверить после первой загрузки.** `004:53`.
- `LowCardinality(String)` — правильный выбор при числе значений до ~10 тыс. (`schema-types-lowcardinality`). Число разных 4-байтовых селекторов цепи за месяцы не измерено. В задачу загрузчика `txs` стоит добавить одну проверку: `SELECT uniqExact(selector) FROM hood.txs`. Если намного больше 10 тыс., то следующей миграцией перейти на `String`, а не обратно на `FixedString`.
