При `--concurrency 1` HEAD и новый код дают одно и то же: 29113 / 13090 в 4 прогонах из 4. Это не регрессия, данные не затрагивает.

### 2. Проверка `eth_chainId` — PASS

- Мок отвечает `0xa4b1` (Arbitrum One). Диапазон, `--gaps`, logs: **выход 1**, в каждом случае ровно 1 HTTP-запрос (`eth_chainId`), запросов блоков и логов 0. В каталоге только пустой `.enricher.lock` (он был и до 020): ни `blocks-*`, ни `logs-*`, ни `filled.tsv`, ни `*.partial`. Текст: `wrong network: the RPC endpoint http://127.0.0.1:18547/… reports chain id 42161 (0xa4b1), expected Robinhood Chain 4663 (0x1237) … Nothing was downloaded`. Логин, пароль и путь URL скрыты (`--rpc-url http://u:secret@…/key123`).
- Для контраста: HEAD с тем же моком вышел с **0** и записал `blocks-100-109.jsonl.zst` и строку в `filled.tsv`. Это и есть тихая порча, которую закрывает п. 2.
- `eth_chainId` отвечает JSON-RPC-ошибкой: повтор, `--max-attempts 3` → 3 запроса, выход 1 (`giving up after 3 attempts`), каталог пуст.
- Входит в `--max-calls`: `--max-calls 21` на 10 блоков → выход 0, ровно 21 вызов. `--max-calls 1` → 1 вызов, выход 75. `--max-calls 0` → 0 вызовов, 75 (сам `eth_chainId` не влез).
- Нет вызова при `--gaps --dry-run` (0 HTTP) и при прогоне без работы (всё в `filled.tsv`, 0 HTTP, выход 0).

### 3. Ошибка планирования бюджета в `--gaps` (1, не 75) — PASS

- Дыры 10 + 5 блоков, `--max-calls 20`: выход **1**, 0 HTTP. Текст: `--max-calls 20 is less than the 21 calls a run needs to commit its largest file (10 blocks x 2 calls + 1 eth_chainId): no run could make progress; lower --chunk to <= 9 or raise --max-calls to >= 21`. Подсказка верна: 9 × 2 + 1 = 19 ≤ 20.
- То же с `--dry-run` — выход 1. `--max-calls 0` — выход 1, подсказка только «raise» (при `max_chunk = 0` вариант с `--chunk` не предлагается).
- HEAD при `--max-calls 20`: 75. Обнаружить это можно было только по журналу.

### 5. Нет ложного раннего 75 при параллельности — PASS

- Сквозной прогон: 239 блоков, бюджет ровно `1 + 2 × 239 = 479`. Варианты: `--gaps --chunk 101 --batch 10 --concurrency 8` и диапазон `--batch 3 --concurrency 16`, по 30 прогонов каждый. Ненулевых выходов 0 из 60, повторов 0.
- Юнит-тест `refused_reserve_does_not_starve_concurrent_ones` падает на старом резерве (мутация выше). Код: `CallBudget::try_reserve` — один `fetch_update` с `checked_add(n).filter(<= max)`, отказ счётчик не трогает.
- Оговорка: при первой попытке стресса мой Python-мок под 16 соединениями давал сбои транспорта (маленький listen backlog). Повторы честно съели бюджет, и получился 75. После `request_queue_size = 512` сбоев нет. Это артефакт мока, а не enricher: повторы входят в бюджет, как и задумано.

### 6. Пауза 429 / Retry-After только по виду ошибки — PASS

- Хэш блока 1001 в моке содержит `429`, первые 2 ответа на чеки — с чужим `blockHash`. Текст причины: `block 1001: receipt 0 blockHash "0xdeadc095…c4294d99…" != 0xa59ec095…c4294d99…` (`429` встречается дважды). Итог: `kind=Transient`, `retries=2`, **`global_pauses=0`**, `rpc_rate_limited=0`, выход 0. Файл совпал с файлом HEAD, в данных хэши согласованы.
- HTTP 429 с `Retry-After: 1` на первые 2 запроса: `http_429=2`, `global_pauses=2`. По времени запросов в моке следующая волна пошла через 1.01 с. Файл идентичен «чистому».
- JSON-RPC `-32005` (ошибка на уровне батча), 2 раза: `rpc_rate_limited=2`, `global_pauses=2`, файл идентичен «чистому».
- Поиска подстрок `"429"` / `"rpc rate limit"` в управляющей логике больше нет (grep по `crates/enricher/src`). Текст идёт только в лог.

### 7. `filled.tsv` мягко, `gaps.tsv` строго — PASS

- **Оборванный хвост `filled.tsv`** (`…\n200\t20` без `\n`). Прогон 1, обе версии: WARN, скачаны 200..209 и 300..304. `append_synced` дописывает `\n` перед новой строкой, поэтому обрывок становится отдельной полной строкой `200\t20`. Прогон 2: **HEAD — выход 1** (`Error: filled file …`), и так на каждом прогоне до ручной правки. **Новый код — выход 0**, 0 HTTP, WARN `ignoring broken line of filled.tsv … line_no=2 line=200\t20 reason=bad range 200..=20`. То есть п. 6 чинит реальный сценарий «один обрыв записи навсегда останавливает `--gaps`», а не только теоретический.
- Битые строки в середине (`20`, `x\ty\tz`): две WARN с номерами строк, скачан только незакрытый диапазон, закрытые 100..109 и 300..304 не перекачаны.
- Можно ли из обрыва получить строку, которая заявляет больше блоков, чем записано? Обрыв по столбцу `to` даёт префикс числа, то есть меньшее число: либо `to < from` (строка битая, пропускается), либо поддиапазон настоящего. Склейки двух строк нет, потому что перед дописыванием в оборванный файл добавляется `\n`. Это вывод из кода `hood_core::fsutil::append_synced` и `parse_range_line`. Сценарий «обрыв → дописывание» проверен прогоном выше. На реально повреждённых дисковых файлах не проверял.
- **`gaps.tsv` строгий**: строка `2x0\t209\t1` → выход 1, 0 HTTP, файлов нет. Текст `gaps file …: line 2: column from is not a number`, как в HEAD. Оборванная последняя строка `gaps.tsv` → WARN, остальное залито. Нет файла gaps → выход 1 (`No such file or directory`).

## Замечания (не блокируют PASS)

**З1. `deploy/enricher-gaps.service`: пропускная способность падает вдвое — исправить до включения таймера.** Проверено прогоном. Дыра 3500 блоков, кусок по умолчанию 1000, `--batch 10 --concurrency 4`:

| Вариант | Выход | Вызовов | Файлов | Блоков за прогон |
|---|---|---|---|---|
| HEAD, `--max-calls 4000` | 75 | 4000 | 2 | 2000 |
| новый, `--max-calls 4000` | 75 | 2001 | **1** | **1000** |
| новый, `--max-calls 4001` | 75 | 4001 | 2 | 2000 |
| новый, `--max-calls 4000 --chunk 999` | 75 | 3997 | 2 | 1998 |
| новый, `--max-calls 1999` | 1 (ошибка конфигурации) | 0 | 0 | 0 |

Рекомендация: **`--max-calls 4001`, а не `--chunk 999`**. С 4001 сохраняется сетка файлов по 1000 блоков (имена `blocks-X-(X+999)` и строки `filled.tsv` согласуются с уже скачанным). `--chunk 999` даёт файлы со сдвинутыми границами и 3 неиспользованных вызова. Ни один из вариантов не оставляет запаса на повторы. Повтор в первом файле лишь не даст начать второй (вызовы не теряются). Но повтор (20 вызовов на батч из 10 блоков) внутри второго файла приведёт к 75 посреди файла и выбросит до ~2000 уже потраченных вызовов. На публичном RPC 429 частые (chain-facts, 2026-09-30). Поэтому разумнее дать запас, например `--max-calls 4201` (1 + 4000 + 10 повторов батча). Это на ~5 % выше суточного потолка: решение по деньгам за Михаилом / infra-ops. В любом случае поправить: комментарий юнита («4000 calls = 2000 blocks per run»), `deploy/README.md` строку 305 («Это 2000 блоков за прогон… 96 000 вызовов в сутки») и пример WARN там же. Теперь в WARN «M more» — это вызовы на весь файл, а не на батч.

**З2. `references/data-model.md` строка 51** по-прежнему говорит «битая строка… ошибка» без различия файлов. Нужна фраза: с 020 битая строка `filled.tsv` пропускается с WARN (диапазон перекачается), `gaps.tsv` строгий. Исполнитель это отметил и отложил до коммита 022/023 — согласен. Строка 52 (коды выхода) верна.

**З3. Устаревшие doc-комментарии в `crates/hood-core/src/ranges.rs`** (020 их не трогала): у `parse_ranges_file_lenient` (стр. 200–203) написано «Only for the recorder's start-up», у `parse_ranges_file` (стр. 218–221) — «The one reading policy for gaps.tsv and filled.tsv». Теперь enricher читает `filled.tsv` мягко. Поправить заодно с З2.

**З4. Режим диапазона: кусок больше бюджета даёт 75, а не 1.** Пример: `--from 100 --to 109 --max-calls 20` → 75 на каждом запуске, без прогресса. Под systemd этот режим не запускается, и это задокументированное изменение (п. 4 отчёта): раньше бюджет тратился, теперь тратится только 1 вызов. Для единообразия можно применить `check_plan_fits_budget` и к диапазону. Рекомендация, не требование.

**З5. (было до 020)** `--dry-run` в режиме диапазона игнорируется и качает данные: и HEAD, и новый код записали файл. В `--help` написано `--gaps: print the plan…`, так что это не ошибка 020. Но легко ошибиться руками. Стоит либо отклонять `--dry-run` без `--gaps`, либо поддержать его в режиме диапазона.

## Предполагается / не проверено

- Что реальный провайдер и публичный RPC отвечают на `eth_chainId` строкой `"0x1237"`. Факт `eth_chainId → 0x1237` есть в `chain-facts.md` (проверено 2026-09-28). В этой проверке к сети не обращался. Нестроковый ответ (число) даст повторы и выход 1: безопасно, но на нестандартном провайдере потребует внимания.
- Поведение под systemd на сервере не проверял: юнит выключен, ssh не использовался.
- Стандартные пункты чек-листа data-auditor (сверка свопов, decimals, дубли ReplacingMergeTree, статусы) к этой задаче не относятся: она не меняет декодеры и таблицы. Применимые части — полнота (нет дыр в записанных диапазонах, `filled.tsv` не опережает данные) и порядок блоков в файле — покрыты пунктами 1, 4, 7, 8.
