## Как проверял

1. `zstd -t` и `zstd -lv` на каждом файле.
2. Свой скрипт (Python, stdlib + `zstd` CLI), независимый от скрипта исполнителя:

   - распаковывает каждый фрейм отдельно;
   - проверяет, что каждый фрейм кончается на `\n`;
   - разбирает каждую строку: 4 столбца, целые числа, валидный JSON;

   - у строк с seq 0 нет `messages`; `payloadBase64` у `recorderFrame` декодируется;
   - монотонность `recv_unix_ns`, дубли, откаты, дыры по всем seq, включая seq внутри конвертов;
   - сверка с `gaps.tsv` и `last_seq.txt`.
3. `feed_audit.py --feed-root data/feed-test-002 --rpc-sample 0` (RPC отключён ещё и `--rpc-url http://127.0.0.1:9`).
4. Разбор оборванного хвоста в `_torn/`.

## Код и тесты

- Фрейм закрывается по таймеру: `frame_due`, `recv_timeout` 500 мс, проверка и в тишине. ## Замечания (не блокируют 002)

**З1 (среднее): строка в `gaps.tsv` может потеряться навсегда.**
- Порядок фиксации: данные fsync → `gaps.tsv`.
- Если процесс убит между этими шагами, в данных уже есть seq после дыры, а строки дыры в `gaps.tsv` нет.
- При старте `recover` берёт точку продолжения как максимум seq из данных и дыры по данным не сверяет. Дыра останется неучтённой.
- Окно узкое (между `sync_data` и записью `gaps.tsv`), но при `Restart=always` и авариях на сервере это возможно.
- Такую дыру обнаружит `feed-audit` (FAIL «gap not listed»), так что тихой ошибки не будет, если аудит идёт регулярно.
- Предложение: при `recover` сверить разрывы seq в последних файлах с `gaps.tsv` и дописать недостающие.

**З2 (низкое): конверт, частично перекрывающий уже записанное, пишется целиком.**
- Пример: seq_first ≤ last_seq < seq_max.
- В сырье появятся повторные seq, `feed-audit` даст FAIL по дублям.
- Бывает только в конвертах из нескольких сообщений, в тесте таких 0. Это согласуется с «сырьё как есть», но в `data-model.md` стоит описать и дедупликацию при разборе.

**З3 (низкое): `write_line` удаляет `\n` и `\r` из сырья (`l.raw.replace(['\n','\r'], "")`).**
- Для компактного JSON фида смысл не меняется: внутри строк JSON переводы строк экранированы.
- Для «непарсящегося текста как есть» это уже не байт-в-байт. Нужно либо описать это в `data-model.md`, либо хранить такой текст в base64 как `recorderFrame`.

**З4 (низкое): граница потерь при kill -9 чуть больше 60 с.**
- Фрейм закрывается, когда с момента его открытия прошло ≥ 60 с. Проверка идёт с шагом до 500 мс.
- Разница между первой и последней строкой фрейма в данных — 60.02–60.10 с.
- Реальная граница потерь — около 60.5 с. В тесте потеряно 58.4 с. Для приёмки несущественно; при желании уменьшить `--frame-secs` до 59.

**Прочее, для сведения:**
- `blocks_per_s = 1.335` и `mb_per_hour = 13.0` у `feed-audit` занижены: в интервал входит 61 мин простоя. За одну сессию получается ~10 блоков/с, это согласуется с отчётом исполнителя.
- `feed-audit` нужно научить строкам с seq 0 (вопрос 3 исполнителя). Пока WARN «unparseable» надо сверять с числом ping + `confirmedSequenceNumberMessage`.
- `fsync` на macOS не сбрасывает кеш диска (нет `F_FULLFSYNC`). Для kill -9 это неважно, для потери питания на Mac — важно. На Linux/ext4 `sync_data` достаточно. Это **предполагается**, на сервере не проверялось.
- Дубли (`seq_max ≤ last_seq`) по-прежнему выбрасываются со счётчиком `dup_skipped`. В тесте их 0. Решение за Михаилом (вопрос 2 исполнителя).
