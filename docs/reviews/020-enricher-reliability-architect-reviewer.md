## Важное

**В1. После 020 `deploy/README.md` и юнит обещают вдвое больше блоков за прогон, чем enricher теперь делает.** Места: `deploy/README.md:305` («Это 2000 блоков за прогон»), `deploy/enricher-gaps.service:32` (`--max-calls 4000`).
Почему важно: раньше 4000 = 2 × 2000. Теперь каждый прогон тратит один вызов на `eth_chainId`, и `fill_blocks` (`lib.rs:225`, `ensure_budget`) не начинает второй файл, потому что на него остаётся 1999 < 2000. За прогон закрывается 1000 блоков, а не 2000, при этом прогон всё равно выходит с 75, то есть «успешно» для systemd. Сама логика верна: без предварительной проверки второй файл съел бы 1999 вызовов и всё равно был бы выброшен. Расходится только эксплуатационный документ. Исполнитель сам это отметил, но вынес вопросом, а не задачей. Юнит сейчас выключен, поэтому замечание не блокирующее. Однако тот, кто включит юнит по README, получит половину ожидаемой пропускной способности и не заметит этого.
Исправление (зона infra-ops, до включения юнита): в `ExecStart` поставить `--max-calls 4001` и поправить комментарий в юните и строку 305 README: «4001 = 1 `eth_chainId` + 2 файла × 2000». Другой вариант — `--chunk 999`. CLI-флаги не меняются, совместимость не ломается. Заодно в README к кодам выхода стоит дописать строку про код 1 при «wrong network» и при `--max-calls` меньше одного файла + 1.

**В2. Литералы с невидимыми табами и переводами строк в тестах.** Места: `crates/enricher/tests/exit_codes.rs:96-101, 119-125, 144-150`, `crates/enricher/tests/gaps.rs:108-114, 116-123, 130-136`.
Почему важно: формат `gaps.tsv`/`filled.tsv` держится на `\t`. Здесь табы стоят буквально внутри многострочных строк, а в соседних тестах того же файла (`exit_codes.rs:37`, `gaps.rs:56`) используется `"100\t103\t1\n…"`. При чтении таб не отличить от пробелов. Редактор или IDE с «tabs → spaces» молча превратит фикстуру в битую строку. Тест `broken_filled_line_is_skipped` при этом может продолжить проходить, но уже по другой причине, а `wrong_chain_id…` упадёт с непонятной ошибкой разбора. Похоже на артефакт инструмента, которым писали файл.
Исправление: вернуть экранированные строки в одну строку кода, например:
```rust
std::fs::write(&gaps, "100\t103\t1\n200\t203\t2\n").unwrap();
std::fs::write(out.join("filled.tsv"), "100\t103\tblocks-100-103.jsonl.zst\t1790000000\n20\nx\ty\tz\n").unwrap();
assert!(filled.starts_with("100\t103\tblocks-100-103.jsonl.zst\t1790000000\n20\nx\ty\tz\n200\t201\t"), "{filled:?}");
```

## Рекомендации

- **Р1. Мёртвый публичный API и второй источник кода 75.** `rpc.rs:164` `pub const EXIT_BUDGET_EXHAUSTED` больше нигде не используется: grep по `crates/enricher` находит только определение, тест, ради которого его оставляли, на него уже не ссылается. Получается второе место, где «живёт» 75, а это противоречит заголовку `exit.rs` («the one place they are defined»). Удалить. `rpc.rs:396` `Rpc::calls_sent()` тоже не используется — удалить или сделать `pub(crate)`. `lib.rs:187` `min_calls_per_run` и `lib.rs:193` `CHAIN_ID_CALLS` объявлены `pub`, но снаружи не нужны — сделать `pub(crate)`/приватными. `CHAIN_ID_CALLS` стоит перенести выше места первого использования.
- **Р2. Режим диапазона: невыполнимый бюджет даёт 75, а не ошибку конфигурации.** `lib.rs:244-252`. В `--from/--to --mode blocks`, если самый большой кусок больше `--max-calls - 1`, прогон тратит 1 вызов на `eth_chainId` и выходит с 75. Повторный запуск снова ничего не продвинет. Для `--gaps` тот же случай с 020 даёт 1. Исправление: вызвать `check_plan_fits_budget(a, &chunks)?` и в ветке `Mode::Blocks` до `connect`. **Меняет поведение:** 75 → 1 только для невыполнимой конфигурации, флаги те же. Режим ручной, поэтому это рекомендация.
- **Р3. Два понятия «минимум вызовов» с похожими именами.** `lib.rs:305` пишет в лог `min_calls` — это вызовы на *весь* план. `min_calls_per_run` (`lib.rs:187`) — вызовы на *самый большой файл + 1*. Переименовать поле лога в `calls_needed_total` и считать через `chunks.iter().map(|c| blocks::calls_needed(*c)).sum()`. Если операторы читают поле `min_calls` (в README его нет, упоминается только `todo_blocks`), это мелкое изменение формата лога.
- **Р4. `blocks.rs:59`**: `((to - from + 1) * 2)` → `* CALLS_PER_BLOCK`, константа уже есть.
- **Р5. Ответ `eth_chainId` с JSON-RPC-ошибкой не из класса rate-limit** (например, -32601 у нестандартного прокси) идёт как `Transient` и повторяется `--max-attempts` раз: при значениях по умолчанию это ~30–60 с бэкоффа и до 8 вызовов бюджета, после чего выход 1. Поведение корректное (ошибка, а не тихий пропуск). Если захочется быстрее падать, можно отдать из `accept` отдельный вид «не повторять». Сейчас усложнять API `Rpc::call` ради этого не стоит, оставить как есть.
- **Р6. `tests/retry.rs:36, 88, 151` по-прежнему меряют реальное время** (~3 с, проверки `elapsed >= 1900ms`). После выноса `next_step` логика паузы покрыта чистыми юнит-тестами, а эти тесты остаются end-to-end проверкой, что `Retry-After` реально соблюдается через HTTP. Переводить их на `start_paused` не советую: auto-advance виртуальных часов вместе с таймаутами reqwest даёт ложные таймауты. Достаточно оставить как есть.
- **Р7 (из R1 исходного ревью, необязательно).** `report()` (`lib.rs:331-364`) всё ещё в `lib.rs`. Перенос в `stats.rs` как `Summary::log()` оставит в `lib.rs` только CLI и оркестрацию. Не срочно.

## Что хорошо (не сломать при правках)

1. **`next_step` — чистая функция**: `(attempt, FailKind, retry_after, &RetryPolicy, u) -> Step { GiveUp | Wait { delay, pause_all } }`. Текст ошибки в решение не входит. Граничные случаи покрыты юнит-тестами (`rpc.rs:633-662`), а интеграционный тест `transient_error_with_429_in_text_does_not_pause_all` с блоком 77429001 ловит именно исходный баг I1. Исполнитель показал, что тест падает на старом коде.
2. **`Rpc::call<T>(…, OnTimeout, accept: Fn(&[Item]) -> Result<T, String>)`**: булева флага нет, каждый результат разбирается один раз, в `blocks.rs`/`logs.rs` нет `unwrap` на ответах RPC, срезы деструктурируются через `let [b, r] = pair else …`. Размеры для статистики пишутся только для принятых батчей. Побайтовый тест формата строки `blocks-*` (`blocks.rs:176`) защищает «сырьё» от случайных изменений.
3. **`CallBudget::try_reserve`** — один `fetch_update` с `checked_add`: отказ счётчик не трогает. Стресс-тест на потоках (`rpc.rs:686`) детерминирован для правильной реализации и падал на старой. Отдельный `check()` без резерва служит только для того, чтобы не начинать файл, который бюджет не оплатит. Это осознанная оптимизация, гонка в ней безвредна.
4. **Проверка `eth_chainId` стоит в правильном месте**: `connect()` вызывается после взятия lock и планирования, но до первого скачивания. В `--gaps` ошибки плана (`--max-blocks`, бюджет) стоят 0 вызовов, а `--dry-run` и пустой план вообще не делают вызовов (проверено тестами `gaps.rs`). При несовпадении сообщение понятное, URL маскируется, ничего не записано (`wrong_chain_id_exits_1_and_writes_nothing`).
5. **`exit.rs`**: значения `u8` и чистая `code(&Outcome)`. В `main.rs` ошибка `report()` идёт только в WARN и код выхода не подменяет. Это проверено интеграционно и для 75 (`stats_json_failure_does_not_mask_exit_75`), и для 130 (`interrupt.rs`, недоступный `--stats-json`).

Мок (`tests/common/mod.rs`) считает `eth_chainId` отдельно и не тратит на него сценарии 429/задержек. Поэтому старые тесты проверяют то же, что и раньше, а явные `chain_id_requests()` фиксируют ровно 1 вызов за прогон.

CLI-флаги не менялись: в диффе `lib.rs` нет ни одной изменённой строки `#[arg]` или поля `Args`, поменялся только doc-комментарий `--max-calls`. Флаги из `deploy/README.md:304` и `deploy/enricher-gaps.service:32` (`--gaps --out-dir --max-calls --rps --batch --concurrency`, плюс `--dry-run` из README:305) на месте. Значения кодов выхода (0/1/75/130) совпадают с `references/data-model.md`, строка «Коды выхода enricher».
