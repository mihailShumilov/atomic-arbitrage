## Важное

1. **[deploy/healthcheck.sh:314–320] Перекрывающиеся строки `filled.tsv` считаются дважды, дыра с пропусками выглядит залитой. Ошибка была до 034, но относится к тому же классу «тихое ok».**
   `cov += hi - lo + 1` суммирует пересечения с каждой строкой без объединения. Проверено 2026-10-05 той же программой на mawk и BWK. Дыра `100..199`, в `filled.tsv` две одинаковые строки `100..149`. Результат `0 0 3`: дыра считается залитой, хотя 50 блоков не залиты.
   Такие повторы возможны. `mark_filled` (`crates/enricher/src/blocks.rs:143`) дописывает строку после каждого закоммиченного файла. Режим диапазона (`--from/--to`) не вычитает уже залитое, поэтому повторный или перекрывающийся ручной прогон в тот же `blocks/` (например, загрузка истории) даёт дубли.
   Rust-сторона считает правильно: `hood_core::ranges::subtract` сначала вызывает `merge`. Получается дубль логики, который разошёлся с Rust по смыслу. Исправление: объединять пересечения внутри дыры, сохраняя формат вывода.
   ```awk
   k = 0
   for (i = 1; i <= nf; i++) {
       lo = ($1 > ff[i]) ? $1 : ff[i]; hi = ($2 < ft[i]) ? $2 : ft[i]
       if (hi >= lo) { k++; L[k] = lo; H[k] = hi }
   }
   for (i = 2; i <= k; i++) {            # insertion sort by lo; k is tiny
       l = L[i]; h = H[i]
       for (j = i - 1; j >= 1 && L[j] > l; j--) { L[j+1] = L[j]; H[j+1] = H[j] }
       L[j+1] = l; H[j+1] = h
   }
   cov = 0; end = $1 - 1
   for (i = 1; i <= k; i++) if (H[i] > end) { s = (L[i] > end + 1) ? L[i] : end + 1; cov += H[i] - s + 1; end = H[i] }
   ```
   Тест для 3c: дыра `76500000..76500999`, в `filled.tsv` дважды строка `76500000..76500499`. Ожидается алерт «500 блоков». Поведение при непересекающихся строках не меняется. Исправить можно в этом же коммите: это тот же блок и тот же сценарий. Если координатор сочтёт это выходом за рамки 034, нужна отдельная маленькая задача. Data-auditor стоит показать этот случай.

2. **[deploy/healthcheck.sh:327–333, 98–101] «awk упал» и «отстаёт» пишут в один ключ `backfill.alert`, поэтому один алерт маскирует другой.**
   `raise` выходит сразу, если `backfill.alert` уже есть. Возьмём сценарий: awk упал, пришёл алерт «не удалось посчитать». На следующем прогоне awk работает, но дозаливка действительно отстаёт. Нового уведомления нет, в состоянии остаётся заголовок «не удалось посчитать». Когда отставание закроется, придёт «восстановлено: не удалось посчитать». В обратном порядке выходит так же. Итог: о реальном отставании человек не узнаёт.
   С самой веткой я согласен: правило «нет тихого ok» верное. Раньше пустые `u_n` в `(( u_n > 0 ))` давали `backfill=ok`. Тест 3c (строки 197–206) это ловит. Сбой редкий, поэтому это «важное», а не блокирующее.
   Исправление на выбор, в порядке простоты:
   - (a) отдельный ключ `backfill_calc`. При сбое вызывать `raise backfill_calc …` и не трогать `backfill`. При успехе вызывать `resolved backfill_calc` и после этого текущую логику `backfill`. В README добавить одну строку;
   - (b) в `raise` повторно уведомлять, если заголовок в `$f` отличается от нового. Это меняет поведение всех проверок, а тексты с цифрами (`$u_n дыр`) будут давать повторы, так что этот вариант хуже.
   Рекомендую (a). Тест: «awk упал» → алерт `backfill_calc`, затем awk работает при незалитой дыре → алерт `дозаливка отстаёт` и «восстановлено: не удалось посчитать».
