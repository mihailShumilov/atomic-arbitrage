## Методика (на проверку data-auditor)

- **Блок часа.** Для часа T берётся блок с `timestamp` в [T, T+60 с); цель — T+25 с (в пробном прогоне T+15 с). Это **не строго «первый блок с `timestamp` ≥ T»**, как в задаче. Чтобы найти именно первый, нужен двоичный поиск на каждый час, ~10 вызовов, а это не помещается в 300. Фактическое смещение `ts − T`: min 0, p10 18, p50 25, p90 32, max 55 с. Для статистики по часу это та же минута; для сверки — номера в `index.tsv`.
- **Системная tx** — только `type` = `0x6a`. **Пользовательская tx** — все остальные. Подклассы (М1): `l2` = `0x0`–`0x4`, `l1` = `0x64`–`0x69` и `0x78`, `other` — прочее. В выборке `l1` = 0 и `other` = 0, поэтому все пользовательские tx подписаны на L2.
- **Откат** — `status` = `0x0` среди пользовательских tx, отдельно по подклассам. Все 5 055 откатов приходятся на `l2`.
- **Своп** — лог с `topics[0]` = v3 Swap `0xc42079f9…` или v4 Swap `0x40e9cecb…`, от любого адреса. Это **логи, а не сделки** (М2), поэтому отдельно считается «tx со свопом/блок». Сделки на кривых launchpad не входят (М3): для торговли это нижняя оценка.
- **Комиссия** — `gasUsed × effectiveGasPrice` пользовательской tx. L1-часть в неё входит, потому что `gasUsed` включает `gasUsedForL1`.
- **Размеры:**
  - «сырой» — компактный JSON `block` и `receipts` с сортировкой ключей, те же байты, что у счётчика enricher;
  - `line_zstd3_b` — строка файла, сжатая **отдельно** CLI `zstd -3`.

  Сплошной файл сжимается лучше. Калибровка «размер файла / сумма отдельно сжатых строк» по 5 готовым файлам 006/003: 0.780, 0.751, 0.800, 0.813, 0.795, в среднем 0.788. «Файл КБ/блок» ниже — это `line_zstd3_b × 0.788`, то есть **оценка**, в интервалах — 0.751…0.813. Для сравнения: файл самой выборки, где блоки разнесены на час, дал 0.877.
- **Веса.** Выборочный блок часа представляет блоки этого часа. Вес = номер блока следующего часа − номер текущего, от 33 775 до 36 399, p50 35 780. Средние взвешены, p10/p50/p90 считаются по 1 392 блокам без весов. Доля откатов «pooled» — Σ откатов / Σ пользовательских tx.
- **Интервалы среднего** — бутстрэп по дням: 58 дней с возвращением, 2 000 повторов, seed 10. Блоки внутри дня скоррелированы, поэтому день берётся целиком.

## Что не получилось / ограничения

- **Не «первый блок ≥ T», а блок в первые 0–55 с часа** (p50 25 с). Причина — бюджет поиска (см. «Методика»). На показатели часа не влияет, но формально это отступление от п. 1 задачи.
- **«Файл КБ/блок» — оценка через калибровку**, а не размер сплошного файла за период. Коэффициент 0.751–0.813 взят с 5 окон. На сутках с другим составом tx он может отличаться. Интервалы в 4.5 этот разброс учитывают, но только в пределах 5 окон.
- **Один блок на час — не среднее за час.** Внутри 20 с разброс ×2–×3 (skeptic 006, 1.1). Поэтому для отдельного часа или дня интервалы широкие. Бутстрэп по дням даёт интервал среднего по периоду, а не по отдельным суткам.
- Доля откатов определяется редкими блоками со всплесками (максимум 282 отката). По 1 блоку в час её среднее за период известно только как 21.8–30.7% (95%).
- Блоки после 30.09 в оценке на 07.10 и 14.10 — расчёт по темпу и размеру последних 7 суток. Не замерено.
- Транзакций типов `0x64`–`0x69` в выборке 0. Подкласс «из L1» определён, но на данных не проверен.

## Предполагается (не проверено)

- Что размер сплошного файла на блок ≈ строка zstd-3 × 0.75–0.81 и на всём периоде (см. выше).
- Что темп и размер блоков 01–14.10 похожи на последние 7 суток. Если после конца субсидии (~29.09) активность изменится, оценка на 14.10 сдвинется.
- Что `gasUsedForL1` = 0 связан с ценой L1-данных в ArbOS (L1 pricer). Механизм не проверял, это гипотеза.
- Что блоки со второй `0x6a` (селектор `0x9998269e`) — отложенные сообщения kind 13 (BatchPostingReport). Так в 006; с фидом не сверял.
- Объём трафика «сырой JSON» верен только без HTTP-сжатия у провайдера (не проверено, skeptic 006, разд. 2).
