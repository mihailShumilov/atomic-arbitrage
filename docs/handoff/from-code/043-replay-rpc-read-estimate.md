## Сделано

1. **Модель чтений.** Трассировок у нас нет: на Free их нет (040), в `data/` тоже. Поэтому для каждой tx строится символьный набор ключей по чекам, логам и известной раскладке хранилища:
   - **аккаунт** — `from`, `to`, каждый эмиттер лога, майнер блока, реализации прокси (WETH, USDG — EIP-1967; Stock Tokens — beacon), хук v4 пула из реестра. Наивный удалённый backend revm (как у foundry) читает по аккаунту 3 значения: `getBalance`, `getTransactionCount`, `getCode`;
   - **слот** — 1 `eth_getStorageAt`. Нижняя модель (L) и верхняя (U) задаются по событиям:

   | Событие / tx | L: слоты | U: дополнительно |
   |---|---|---|
   | ERC-20 `Transfer` | balance[from], balance[to] (mint/burn — totalSupply) | allowance, если from ≠ tx.from; слот impl прокси у неизвестных токенов; 3 флага pause/freeze у USDG и Stock Tokens |
   | WETH `Deposit`/`Withdrawal` | balance | аккаунт получателя ETH |
   | v3 `Swap` | slot0, feeGrowthGlobal, protocolFees, liquidity, observation, слово tickBitmap текущего тика (6) | 2 соседних слова bitmap, второй feeGrowth, следующая observation, 2 пересечённых тика × 4 слота (+13) |
   | v4 `Swap` (PoolManager) | `pools[id]`: slot0, feeGrowthGlobal, liquidity, слово bitmap (4); хук: аккаунт + 1 слот | 2 слова bitmap, второй feeGrowth, protocolFeesAccrued, 2 тика × 4; хук +5 слотов; у неразрешённого пула — неизвестный хук |
   | Mint/Burn/Collect v3, ModifyLiquidity v4 | 6 | +14 |
   | Неизвестное событие | 1 у эмиттера | +3 |
   | Откатившаяся tx (логов нет) | 1 слот у `to` | +10 слотов, +3 аккаунта |
   | Своп-tx | — | Permit2 и неизвестный помощник: +2 аккаунта, +3 слота |
   | ArbOS `0x6a` | **исключено** (см. допущения) | — |

2. **Проверка модели по газу.** Это жёсткий потолок, без трассировок. Каждый уникальный слот в tx стоит ≥ 1 900 газа (холодный SLOAD 2 100, надбавка к холодному SSTORE или предпрогрев через access list 1 900), аккаунт — ≥ 2 400. Отсюда потолок ключей на tx: `2 + (gasUsed − gasUsedForL1 − intrinsic) / 1900`.
3. **Три режима кеша:**
   - холодный блок: на каждый блок кеш с нуля, состояние берётся на N−1;
   - тёплый: подряд W блоков с общим кешем. Значение, прочитанное на старте, остаётся верным: всё, что его меняет, исполняется локально;
   - только целевые пулы: состояние пула ведётся точной математикой по событиям, RPC нужен только для начального снимка.
4. **Пересчёт** в CU, время на Free и PAYG и в доллары. Для других провайдеров (Dwellir и OrbitFlare, 042 заблокирована) дана общая формула «чтения / rps».

**Режим C как основа горячего пути — преждевременно.** Это кандидат для ванильных v3/v4-пулов в исследовании, рядом с revm или серверной симуляцией для хуков и кривых. Решать до калибровки, до декодеров ликвидности и до выбора источника логов у головы рано. Причины (ревью skeptic-analyst, В7):
1. **Хуки:** 18% строк свопов и 40% строк v4 (036: 1 922 из 4 756 строк v4, из 10 610 всего). Из них Pons v2 — 1 242, Doppler — 87, прочие — 593.
   - **Pons v2:** комиссия берётся хуком вне AMM. В событии `fee` = 0, а `HookFeeCollected` ≈ 1% ETH-ноги (036, одна tx). Параметры у каждого запуска свои.
   - **Doppler:** динамическая комиссия (`0x800000`) и перебалансировка ликвидности внутри хука.
   - Цену и ликвидность после свопа события дают, а сумму, которую получит наша сделка через хук, — нет. Хранилище хука из событий не вывести.
   - По правилу движка такие пулы либо честно симулируются через revm (или сервер), либо явно исключаются. Pons v2 — центр исследования импульса, поэтому исключение бьёт по главной задаче.
2. **Кривые Pons v2 до выпуска — не v3/v4-пулы:** 377/323 эмиттера `CurveBuy`/`CurveSell`, у каждой своя формула и состояние.
3. **Декодеров `Mint`/`Burn`/`ModifyLiquidity` нет.** Без них `liquidityNet` по тикам неизвестен, и правило 3 бэктеста не выполнить.
4. **Форки v3** (189 эмиттеров, 035) не разобраны.
5. **Живой режим** всё равно требует источника логов у головы. Тезис «один код без зависимости от RPC» для фазы 2 неверен.
6. За режим C: порядок `(block, tx_index, log_index)` даёт точное состояние ванильного пула после tx k блока B+1 (правило 2), и дёшево. Ни один RPC-путь так не может.

## Предполагается (не проверено)

- **Модель ключей не сверена с трассировкой.** Не видны: контракты без событий (агрегаторы, квотеры, оракулы, Permit2, хуки без событий), реальное число пересечённых тиков, хранилище хуков. Потолок по газу (~×3 к U) — единственная твёрдая граница, и та не железная:
  - `gasUsed` считается после возврата за очистку слотов, до 1/5 газа, так что потолок может быть занижен до ~25%;
  - чтения ArbOS внутри прекомпилов стоят 800 газа (по исходникам Nitro, не проверено).
- **Откаты (21–26% tx):** по собственному потолку газа они читают **не больше ~3× U** (потолок 27 ключей на tx при U 25 чтений). Прежний тезис «в разы больше U» снят. Откаты — 10% газа L2, бьют в несколько контрактов, для холодного блока это плюс ~10–30% к L.
- Пол `nonce = 0` верен для наивного backend'а. Если знать «аккаунт пуст» из своих данных, читать его не нужно.
- Удалённый backend revm читает аккаунт тремя вызовами. Вариант «1 вызов» (`eth_getProof` / `eth_getAccount`) и дешёвые способы из таблицы 4 на Nitro не проверены.
- **ArbOS, прекомпилы, Stylus — вопрос корректности, а не только числа чтений.**
  - revm не исполняет tx `0x6a` и `0x64`–`0x69`, прекомпилы ArbSys/ArbGasInfo, Stylus (WASM);
  - `block.number` в EVM Nitro — номер L1-блока (не проверено);
  - одна неверно эмулированная операция незаметно портит тёплый кеш до конца окна;
  - есть ли Stylus среди затронутых контрактов, офлайн не видно.

  Серверная симуляция этих проблем не имеет.
- Экстраполяция тёплого кеша с 200–300 блоков на час и на 53 млн блоков — степенная подгонка (показатель 0.68–0.93). Верхний край ограничен только валовой суммой холодных чтений (9.6–20 млрд).
- Окна `data/blocks` выбраны не случайно. 500 из 1 320 блоков подряд — 29–30.09, устойчивость после 29.09 не проверена.
- Набор пулов (3 847 наблюдавшихся) — смещённая выборка. Нужен полный список по `Initialize`/`PoolCreated`.
