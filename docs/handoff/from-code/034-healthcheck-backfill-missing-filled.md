# 034 — healthcheck: `backfill` молчит при отсутствующем/пустом `filled.tsv` (отчёт)

Дата: 2026-10-05. Исполнитель: infra-ops. База: HEAD `5f58293`. Изменения не закоммичены, коммит делает координатор. Статус задачи не менял, ревьюеров (architect-reviewer, data-auditor) не запускал.

Фид, RPC и ssh не использовались, на сервер ничего не выкладывалось. Изменены только файлы в `deploy/` и этот отчёт.

## Сделано

1. **`deploy/healthcheck.sh`, блок `backfill` (строки ~296–336).**
   - `filled.tsv` теперь отличается от `gaps.tsv` по имени файла (`FILENAME == ARGV[1]`), а не по `FNR == NR`. Подстановка `/dev/null` вместо отсутствующего файла осталась: mawk падает на несуществующем файле. Но теперь строки `gaps.tsv` никогда не попадают в «залитые». Итог: если `filled.tsv` нет, он пустой, в нём только заголовок или он не читается пользователем `hood`, то все дыры старше порога считаются незалитыми.
   - В тело алерта добавлено состояние `filled.tsv`: `<путь> — нет.`, `— не читается.` или `— диапазонов: N.`. Остальной текст подсказки прежний.
   - Добавлена новая защита от тихого ok (в задаче её не было, добавил сам; ревьюеру стоит подтвердить). Если awk не вернул чисел (упал), раньше пустые `u_n` в `(( u_n > 0 ))` давали 0 и `backfill=ok`. Теперь в этом случае приходит алерт «не удалось посчитать отставание дозаливки». После ревью он идёт под отдельным ключом `backfill_calc`, см. «Правки после ревью».
   - Формула покрытия, порог `HC_BACKFILL_MAX_LAG_H` и ключ состояния `backfill.alert` не изменились.
2. **`deploy/test/test-healthcheck.sh`, раздел 3c (строки ~156–216).** Проверяемые случаи по порядку:
   - нет `filled.tsv` → один алерт «1 дыр, 1000 блоков», в теле `нет`, `backfill=BAD`, повтора нет;
   - полное покрытие → «восстановлено»;
   - пустой файл → алерт, в теле `диапазонов: 0`;
   - только заголовок → остаётся BAD;
   - полное покрытие → «восстановлено»;
   - частичное покрытие без строки-заголовка (первая строка — данные) → алерт «500 блоков», `диапазонов: 1`, затем «восстановлено»;
   - две старые дыры и пустой `filled.tsv` → алерт «2 дыр, 1100 блоков». Это ровно сценарий Б3: раньше первые строки `gaps.tsv` читались как диапазоны;
   - сбой awk (заглушка, которая роняет только вызов `backfill`) → алерт «не удалось посчитать», затем «восстановлено»;
   - `filled.tsv` с правами 000 (только не под root) → алерт, в теле `не читается`, затем «восстановлено». Под root этот случай пропускается (`SKIP`).
3. **Поиск того же приёма (п. 3 задачи).** Проверено 2026-10-05 через `grep`:
   - в `deploy/` `FNR == NR` был только в `healthcheck.sh:301`, его исправил;
   - остальные awk в `deploy/` читают один файл;
   - `feed_audit.py` и `SKILL.md` скилла feed-audit `filled.tsv` не читают (0 вхождений), awk в них нет;
   - в `deploy/README.md` такого приёма нет;
   - вне `deploy/` тот же awk `FNR==NR` есть в командах проверки отчёта `docs/handoff/from-code/030-fill-restart-gaps-public-rpc.md:82`. Я его не правил: это чужой отчёт и вне рамки задачи. Data-auditor в ревью 030 (п. 8) уже дал к нему отрицательный контроль. Этот awk можно заменить командой healthcheck из раздела «Команды» ниже.
4. **`deploy/README.md`**, строка `backfill` в таблице «Мониторинг»: описано новое поведение (нет, пустой или нечитаемый файл означает «всё незалито»; состояние `filled.tsv` в тексте; алерт при сбое подсчёта).

## Предполагается / не проверено

- **Состояние сервера.** По ревью 030 на сервере, скорее всего, нет `filled.tsv`, а в `gaps.tsv` есть две дыры (733 блока) старше 24 ч. Если 034 выложить **до** выкладки данных 030, при первом же прогоне healthcheck придёт ALERT `backfill` «2 дыр, 733 блоков». Это правильный сигнал, а не сбой. Если 030 уже выложена (`filled.tsv` покрывает обе дыры), алерта не будет. Если алерт пришёл и после 030, значит в `gaps.tsv` есть другие незалитые старые дыры, и их нужно посмотреть.
- **Права.** Healthcheck работает от `hood`. Если `filled.tsv` после 030 принадлежит root с режимом 0600, теперь придёт алерт с текстом `не читается`, а раньше было бы тихое ok. Команда проверки прав есть ниже.
- Путь «awk упал» на сервере не воспроизводился, только заглушкой в тесте.
- Стенд `run-systemd-container.sh` не запускал: юниты и bootstrap не менялись, изменён только скрипт, который bootstrap копирует через `install_file`.

## Команды для Михаила

Выполнять после rsync чистого клона координатором. Recorder не перезапускается. С сервера к фиду и RPC ничего не подключается, healthcheck читает только локальные файлы.

```bash
srv# chown -R hoodbuild:hoodbuild /opt/hoodchain-mev/src
srv# systemctl show recorder -p NRestarts -p ActiveEnterTimestamp -p MainPID > /root/rec-before.txt
srv# bash /opt/hoodchain-mev/src/deploy/bootstrap.sh
#    ожидается от 034: CHANGED /opt/hoodchain-mev/deploy/healthcheck.sh и /opt/hoodchain-mev/deploy/README.md, без daemon-reload
#    (плюс то, что ещё не выложено из других задач, если они меняют deploy/)
srv# bash /opt/hoodchain-mev/src/deploy/bootstrap.sh | tail -n 1      # done: 0 change(s)
srv# systemctl show recorder -p NRestarts -p ActiveEnterTimestamp -p MainPID | diff /root/rec-before.txt - && echo "recorder не тронут"

# hood должен читать filled.tsv (если файл есть)
srv# ls -l /srv/hood/data/blocks/filled.tsv; runuser -u hood -- test -r /srv/hood/data/blocks/filled.tsv && echo readable

# Отрицательный контроль без уведомлений: временный каталог состояния, notify = true, filled.tsv «нет».
# Ожидается backfill=BAD, если в gaps.tsv есть дыры старше 24 ч (на старом скрипте здесь было бы backfill=ok)
srv# runuser -u hood -- bash -c 'd=$(mktemp -d); HC_CONFIG=/nonexistent HC_STATE_DIR=$d HC_NOTIFY=/usr/bin/true HC_BLOCKS_DIR=/nonexistent /opt/hoodchain-mev/deploy/healthcheck.sh | tail -n 1; rm -rf "$d"'
# То же с настоящим filled.tsv: backfill=ok, если все старые дыры залиты (после 030), иначе backfill=BAD
srv# runuser -u hood -- bash -c 'd=$(mktemp -d); HC_CONFIG=/nonexistent HC_STATE_DIR=$d HC_NOTIFY=/usr/bin/true /opt/hoodchain-mev/deploy/healthcheck.sh | tail -n 1; rm -rf "$d"'

# Настоящий прогон, уведомления идут как обычно
srv# systemctl start healthcheck.service && journalctl -u healthcheck.service -n 3 -o cat
srv# ls /var/lib/hoodchain/health/                                    # backfill.alert есть, только если дозаливка правда отстаёт
```

Временный каталог состояния нужен в ручных прогонах, чтобы не трогать `/var/lib/hoodchain/health`: тогда `gaps.offset` и `*.alert` настоящего таймера не меняются. С `HC_CONFIG=/nonexistent` берутся пороги по умолчанию и пути `/srv/hood/data/...`. `HC_HEARTBEAT_URL` при этом пустой, сети нет. Прочие ключи в итоговой строке ручного прогона (например, `clock`) могут отличаться от таймера, смотреть нужно только на `backfill=`.

## Вопросы

- Подтвердить алерт при сбое подсчёта («не удалось посчитать отставание дозаливки»). В задаче его не было. Это сознательное правило «нет тихого ok».
- Порядок выкладки 034 и данных 030. Если 034 пойдёт первой, ALERT `backfill` по двум дырам 030 придёт сразу и закроется «восстановлено» после выкладки 030. Это заодно живая проверка Б3.

## Правки после ревью

Источник: `docs/reviews/034-healthcheck-backfill-missing-filled-architect-reviewer.md`, вердикт PASS, два замечания «важное» и рекомендации. Правки сделаны 2026-10-05, затронуты только файлы в `deploy/`.

- **Важное 1: перекрывающиеся и повторные строки `filled.tsv`.** Раньше пересечения дыры со строками просто суммировались, и повтор строки давал тихое ok. Теперь покрытие считается как объединение пересечений: пересечения сортируются вставками по `lo`, затем идёт один проход с `end`. Это тот же смысл, что `merge` + `subtract` в `hood_core::ranges`. Формат вывода awk прежний (`n b nf`). Тесты в 3c:
  - строка 76500000..76500499 дважды → алерт «1 дыр, 500 блоков», в теле `диапазонов: 2`;
  - три перекрывающиеся строки не по порядку, одна вложенная, в объединении не хватает 100 блоков → алерт «100 блоков»;
  - перекрывающиеся строки, вместе покрывающие всю дыру → «восстановлено», `backfill=ok`.
- **Важное 2: отдельный ключ `backfill_calc`.** Сбой awk теперь вызывает `raise backfill_calc` и не трогает `backfill`. В итоговой строке ключа `backfill` при этом нет, файл `backfill.alert` остаётся как был. При успешном подсчёте вызывается `resolved backfill_calc`, затем прежняя логика `backfill`. Проверены оба порядка:
  - (A) сбой → алерт `backfill_calc`, `backfill.alert` нет, повтора нет. Затем подсчёт работает при реальном отставании → два уведомления: «восстановлено: не удалось посчитать» и алерт «дозаливка отстаёт: 2 дыр, 1100 блоков»;
  - (B) отставание уже поднято, затем сбой → отдельный алерт `backfill_calc`, `backfill.alert` сохраняет заголовок отставания. Затем всё залито → два «восстановлено», `backfill=ok backfill_calc=ok`.
- **Рекомендации.**
  - Рядом с `-v cutoff` добавлен комментарий: заглушка awk в 3c узнаёт вызов по аргументу `cutoff=`.
  - В шапку `healthcheck.sh` добавлено правило: объединение строк; нет, пустой или нечитаемый файл означает «ничего не залито». Добавлена строка о ключе `backfill_calc`.
  - `filled_state` задаётся в одной развилке после awk. Поведение то же.
- **README**: в строке `backfill` описано объединение строк, добавлена строка `backfill_calc`.
