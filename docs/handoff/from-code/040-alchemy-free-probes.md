### П. 1: что этот замер может и чего не может

- **«~60 мс» между блоком и чеками — не задержка.** Чеки head запрашивались после ответа на блок head. 55–75 мс — это время одного вызова. Значит, к моменту запроса чеки уже были, и только.
- **Отбор.** Запрашивались только блоки, которые `eth_blockNumber` уже объявил головой. Окно «блок объявлен, чеков ещё нет» короче ~80 мс замер не видит. Ответила ли на запрос та же нода за балансировщиком, тоже не видно.
- **head+1** — блок, который в момент ответа `eth_blockNumber` ещё не был головой. Он отдавался с полными чеками в 3 из 3 запросов, в том числе через 1.2 мс после ответа `eth_blockNumber`. Так быстро блок мог успеть появиться, мог и не успеть. Или запрос ушёл на другую ноду с более свежей головой. Это не различить.
- **Несуществующий блок (head+10)** даёт HTTP 200, `{"result":null}`, без `error`. Клиент потока должен понимать `result: null` как «блока ещё нет». Ответ пришёл за 527 мс, против обычных 50–90 мс. Причина не установлена, наблюдение одно.
- **Выборка.** 11 запросов чеков у головы, `null` — 0. По «правилу трёх» доля `null` ниже ~27% (95%). Редкие `null`, например раз на 100 блоков, не исключены. Условия: блоки 4–14 tx, 11:23–11:33 UTC, вне пика 14–19 UTC. Тяжёлые блоки и устойчивость часами не проверены.
- **Отставание головы от `timestamp`.** Считаю по времени ответа `eth_blockNumber` (пересчёт skeptic-analyst):
  - в раунде 1 ≤ 195 мс: head — первый блок новой секунды;
  - в раунде 3 ≥ 175 мс (до 1 175 мс);
  - в раундах 0 и 2 ≤ 914 и ≤ 681 мс.

  Итого ~0.2–1.2 с, это 2–12 блоков. Исходит из допущения, что `timestamp` — секунда, округлённая вниз (для Nitro не проверено). С временем прихода из фида не сравнивалось.

- Архив post-state v3: 17 из 17 на 4 глубинах, storage = `eth_call`. Как: офлайн-декодирование `raw/D*`.
- Архив v4: `extsload` = `Swap` того же блока, 3 поля из 3. Как: офлайн-разбор `data/blocks/blocks-27607293-27607492.jsonl.zst` и `raw/G*`. Слот = `keccak256(poolId ‖ 6)`, селектор `0x1e2eaeaf` посчитан локально (pycryptodome).

## Предполагается (не проверено)

- `timestamp` блока Nitro — секунда, округлённая вниз от момента производства.
- Nitro не реализует `trace_*` для Nitro-блоков.
- `debug_*` для Robinhood на PAYG: нет данных ни за, ни против, кроме списка методов (против).
- Причина ответа за 527 мс на несуществующий блок.
- Даты глубин «~1 сут / ~1 нед / ~1 мес» — по средней частоте блоков.
- Списываются ли CU за ответы HTTP 400.

## Что не получилось

- Отставание от фида не измерено: сервер в этой задаче не трогал.
- Выборка у головы мала для выводов об устойчивости. Нужен замер с `hood-rec` в часы пика, а это разрешение Михаила (разбор 040, раздел 6).
