## Зачем
По 005 публичный фид соблюдает `Arbitrum-Requested-Sequence-Number` внутри бэклога (~60–70 с). Если recorder будет просить `last_seq+1` при каждом подключении, короткие обрывы закрываются без RPC. Это последняя доработка recorder перед деплоем на сервер и стартом 7-суточной записи.

## Контекст
- `docs/handoff/from-code/005-feed-requested-seq-test.md` (раздел «Код Nitro», предложение п. 1), `docs/reviews/005-feed-requested-seq-test-data-audit.md` (З1–З3).
- Nitro-клиент шлёт ровно `Arbitrum-Feed-Client-Version: 2` и `Arbitrum-Requested-Sequence-Number: <десятичное>`. Сервер Robinhood без заголовка начинает у tip; при N старше бэклога — молча отдаёт весь бэклог с начала.
- `docs/reviews/008-recorder-feed-fixes-data-audit.md`: Р1–Р3 и «idle-таймаут рвёт соединение без Close».

## Что сделать
1. **Заголовки.** При каждом подключении (в том числе первом после старта, если в данных есть `last_seq`) слать `Arbitrum-Feed-Client-Version: 2` и `Arbitrum-Requested-Sequence-Number: last_seq + 1`. Источник `last_seq` — память процесса, при старте — результат `recover` (из данных, не из `last_seq.txt`). Нет данных — заголовок не слать. Флаг `--no-requested-seq` отключает.
2. **Учёт досылки.** В событие `connected` в `connections.tsv` добавить requested, первый полученный seq и сколько блоков пришло из бэклога (seq ≤ seq на момент первой паузы > 30 мс, как в аудите 005, или проще — до первого кадра, чьё `header.timestamp` отстаёт < 2 с; выбери и опиши). Повторы (seq ≤ last_seq) — уже существующий `dup_skipped`, дыры — как сейчас через `accept`. Формат строки сырья не меняется.
3. **Р1 (feed-audit).** Перед сверкой склеивать смежные и перекрывающиеся строки `gaps.tsv`.
4. **Р2.** В валидном JSON удалять и `\t` (в JSON сырой TAB может быть только незначащим пробелом, как `\n`/`\r`). Описать в `data-model.md`.
5. **Р3 (feed-audit).** Фрейм прошлого часа считать открытым, если аудит запущен раньше `HH:00 + frame-secs + 60 с` и в файле текущего часа ещё нет строк; без FAIL, с пометкой.
6. **Close при idle-таймауте** и при любом другом обрыве по инициативе клиента: Close 1000 (или 1001) → ожидание ≤ 2 с → `ws.close()`, как при остановке. Событие `client_close`.
7. **chain-facts.md** — поправить запись о бэклоге по аудиту 005 (З1, З2): «в двух замерах (16:37 и 16:41Z 30.09) бэклог ≥ 597 и ≥ 662 блока до tip RPC, фактически ~615–690 (~63–69 с); глубина может меняться; соблюдение заголовка внутри бэклога проверено одной точкой (N = tip−100)».
8. **Живая проверка, с Mac** (не прод-IP; сервер ещё не развёрнут):
   - папка `data/feed-test-009` (новая);
   - сессия A: запись 10 мин → SIGTERM;
   - recorder сразу перезапускается и сам выжидает `--min-connect-interval-secs` (120 с, не уменьшать);
   - сессия B: 5 мин → SIGTERM;
   - ожидание: заголовок ушёл с `last_seq+1`; первый seq сессии B = начало бэклога (простой ~2+ мин длиннее бэклога); в `gaps.tsv` ровно одна строка от `last_seq_A+1` до `первый_seq_B−1`, и она заметно короче, чем была бы без заголовка (сравнить с seq у tip в момент подключения B — из первых кадров с малым отставанием `header.timestamp`);
   - `feed-audit --rpc-sample 0` по папке — PASS.

## Что НЕ делать
- Не больше **2** подключений к основному фиду за задачу; не уменьшать паузу 120 с; не подключаться к delayed-feed (это отдельное решение по 004).
- При 403 или 429 — остановиться, ничего не повторять, описать в отчёте и в `chain-facts.md` как факт (время, пауза перед подключением, был ли Close в прошлой сессии).
- RPC — не больше 20 вызовов (сверка нескольких blockHash по желанию data-auditor).
- Не трогать `data/feed`, `data/feed-test-002`; enricher и `hood-core` не менять без необходимости.
