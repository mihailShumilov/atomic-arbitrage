# 008 — recorder и feed-audit: исправления по аудитам 002 перед круглосуточной записью

## Зачем
Прежде чем начинать 7-суточную запись (критерий фазы 1a), нужно закрыть замечания аудита 002, которые могут тихо испортить данные или дать час простоя, и научить `feed-audit` новому формату сырья. Иначе ежедневный аудит будет шуметь, а бан после рестарта повторится на сервере.

## Контекст
- Отчёт `docs/handoff/from-code/002-recorder-hardening.md` и аудит `docs/reviews/002-recorder-hardening-data-audit.md` (замечания З1–З4, «Прочее»).
- `chain-facts.md` [проверено 2026-09-30, задача 002]: бан IP — `403` + `Retry-After: 3600` на переподключении через 11 с после `kill -9`; 429 перед ним не было; причина не установлена (гипотезы: частота подключений; обрыв без close-фрейма).
- За ~20 мин живой записи (001 + 002) сервер ни разу не закрыл соединение сам.
- Тестовые данные: `data/feed-test-002` (одна настоящая дыра 76532007..76568582, 311 строк с seq 0, `_torn/`), `data/feed` (запись 001, старый формат: один фрейм на час).

## Что сделать
1. **З1 — сверка дыр при старте.** В `recover` пройти по seq в двух последних часовых файлах (тех же, что проверяются на оборванный хвост) и в конце предыдущего файла на стыке; каждый разрыв seq, которого нет в `gaps.tsv`, дописать туда (формат `from \t to \t recv_ns`, `recv_ns` — первой строки после дыры) с fsync. Событие `gap_reconciled` в `connections.tsv` и WARN в лог. Разрыв на стыке «конец данных → первый seq новой сессии» по-прежнему пишет `accept`, двойной записи быть не должно.
2. **Пауза между подключениями переживает рестарт всегда, а не только после ошибки.** Новый флаг `--min-connect-interval-secs` (по умолчанию 120): при старте взять время последнего события `connected` из `connections.tsv`; если прошло меньше — ждать остаток (событие `startup_wait`, причина `min_connect_interval`). `--ignore-pending-pause` отключает и это.
3. **Close-фрейм при остановке.** Проверить по коду и тестом на локальном моке, что на SIGINT/SIGTERM recorder отправляет WebSocket Close (1000) и дожидается ответа ≤ 2 с, прежде чем рвать TCP. Если не отправлял — добавить. В отчёте явно: было / стало.
4. **systemd.** В `deploy/recorder.service` `RestartSec=120`; в `deploy/README.md` — почему (бан 403/3600, п. 2). Комментарий про «limit is 2, the 3rd gets 429» пометить как непроверенный (факт из потерянной сессии).
5. **З4.** Гарантировать, что фрейм закрывается не позже чем через `--frame-secs` после первой строки (проверять срок с учётом шага таймаута; например, коммитить, если до срока осталось меньше шага). Потери при kill -9 — ≤ 60 с. Юнит-тест на границу.
6. **З3.** Текстовый фрейм, который не парсится как JSON, писать как `recorderFrame` с `opcode:"text"` и `payloadBase64`, а не «как есть» с вырезанными `\n`/`\r`. Валидный JSON — как раньше.
7. **З2 — только документация.** В `references/data-model.md` описать: частично перекрывающий конверт пишется целиком; дедупликация по `sequenceNumber` — обязанность разбора/загрузчика.
8. **feed-audit** (`.claude/skills/feed-audit/`):
   - строки с seq 0 разбирать по типам: `recorderFrame:<opcode>`, `confirmedSequenceNumberMessage`, прочее; в выводе отдельные счётчики; WARN только для «прочего»; в `envelopes` их не считать;
   - блоки/с и МБ/ч считать по времени сессий (интервалы между соседними строками больше N с, по умолчанию 30, исключать; если есть `connections.tsv` — по нему), а общий интервал выводить отдельно;
   - целостность проверять по фреймам: целые фреймы + открытый хвост текущего часа (≤ 1 фрейма) — не FAIL; оборванный хвост в закрытом часе — FAIL;
   - игнорировать `_torn/`, `connections.tsv`, `*.tmp`;
   - обновить `SKILL.md` (убрать устаревшее «файл текущего часа всегда FAIL»).

## Что НЕ делать
- **Ни одного подключения к фиду и ни одного вызова RPC.** Всё — юнит-тесты, локальный мок (`ws://127.0.0.1`), офлайн-прогоны `feed-audit` с `--rpc-sample 0`.
- Не запускать recorder в `data/feed` и не менять файлы в `data/feed` и `data/feed-test-002` (для тестов — копии в scratch).
- Не трогать enricher, `hood-core` (кроме крайней необходимости — тогда объяснить), формат строки сырья и имена файлов.
- Не решать открытые вопросы 002: сохранение дублей и спасение строк из `_torn/` — остаются за Михаилом.

## Критерии приёмки
- `cargo test --workspace` и `cargo clippy --workspace --all-targets -- -D warnings` чистые.
- Тест З1: синтетические данные с разрывом seq без строки в `gaps.tsv` → после `recover` строка появилась ровно одна; повторный старт ничего не дописывает.
- Тест п. 2: `connections.tsv` с `connected` 30 с назад → ожидание ≈ 90 с; SIGTERM прерывает ожидание, выход 0.
- Тест п. 3: мок видит Close 1000 от клиента при SIGTERM.
- `feed-audit --rpc-sample 0` на `data/feed-test-002`: PASS без WARN про unparseable; счётчики ping = 285, confirmedSequenceNumberMessage = 26; блоки/с по сессиям ≈ 10. На `data/feed`: PASS, как в 001.
- data-auditor: PASS по пунктам 1, 3, 5, 6, 8 (чтение кода + тесты + свой офлайн-прогон на копиях).
