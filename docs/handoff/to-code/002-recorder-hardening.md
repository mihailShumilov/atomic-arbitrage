## Зачем
Прежняя сессия Claude Code сделала recorder устойчивым, но эта версия потеряна. Без этого нельзя запускать круглосуточную запись: при kill -9 теряется хвост часа, частые переподключения ведут к 429 и бану IP примерно на час.

## Контекст
- `crates/recorder/src/main.rs`: `HourWriter` держит один zstd-энкодер на час; `run_connection` пропускает нетекстовые фреймы и конверты без `messages` (`continue`); пауза переподключения 250 мс → 30 с.
- Со слов прежней сессии (перепроверяется в 006, пока гипотеза): фид сам регулярно закрывает соединение; пропущенное после переподключения не досылает; частые переподключения получают 429; после накопления отказов — бан IP ~1 ч (403 или отказ апгрейда).
- `references/data-model.md`: формат сырья неизменяем — строка `recv_unix_ns \t seq_first \t seq_last \t <JSON>`.

## Что сделать
1. **Фреймы zstd раз в минуту.** Закрывать текущий zstd-фрейм не реже раза в 60 с (и при ротации часа), делать `fsync`. Файл остаётся часовым, внутри — много фреймов.
2. **Восстановление после kill -9.** При старте, если последний часовой файл заканчивается оборванным фреймом, обрезать его до конца последнего целого фрейма (оставив копию оборванного хвоста в `data/feed/_torn/` для разбора). `last_seq.txt` писать атомарно (tmp + rename) и только после `fsync` данных, которые он описывает — состояние не должно опережать данные.
3. **SIGTERM.** Обрабатывать SIGTERM так же, как SIGINT: дописать очередь, закрыть фрейм, `fsync`, записать `last_seq.txt`.
4. **Паузы.**
   - Обычное закрытие сервером: пауза 1–5 с с джиттером.
   - 429: соблюдать `Retry-After`, если есть; иначе экспоненциальная пауза 5 → 10 → 20 → 40 → 60 мин (потолок 60 мин).
   - 403 / отказ апгрейда: та же лестница, но начиная с 15 мин.
   - Успешное соединение дольше 10 мин сбрасывает лестницу.
   - Все события переподключения писать в `data/feed/connections.tsv`: время, причина, HTTP-код, `Retry-After`, выбранная пауза.
5. **Ничего не выбрасывать.** Конверты без `messages` (например, только `confirmedSequenceNumber`) и нетекстовые фреймы сохранять: первые — в основной файл с `seq_first = seq_last = 0`, вторые — base64 с пометкой типа фрейма. Сырьё неизменно, фильтрация — на этапе разбора.
6. **Непрерывность внутри конверта.** Если в конверте несколько сообщений, проверить, что `sequenceNumber` идут подряд; разрыв внутри конверта писать в `gaps.tsv` так же, как между конвертами.
7. **systemd-юнит** `deploy/recorder.service`: `Restart=always`, `RestartSec=30`, `KillSignal=SIGTERM`, `TimeoutStopSec=30`, лог в journald. Плюс `deploy/README.md` — как поставить.
8. Тесты: обрезка оборванного фрейма (синтетический файл); лестница пауз (чистая функция); разрыв внутри конверта; конверт без `messages` сохраняется.

## Что НЕ делать
- Не менять формат строки сырья и имена файлов.
- Не тестировать баны и 429 намеренно (не провоцировать сервер). Логику пауз проверять юнит-тестами.
- Не открывать больше одного соединения (два соединения — задача 004).

## Критерии приёмки
- `cargo test`, `cargo clippy -D warnings` чистые.
- Ручной тест: запись 5 мин → `kill -9` → перезапуск → все файлы читаются `zstd -dc` целиком, потеряно не больше последних 60 с, дыра простоя в `gaps.tsv`.
- Ручной тест: `kill -TERM` → потерь нет, `last_seq.txt` = последний записанный seq.
- data-auditor: PASS по пунктам «файлы читаются целиком», «last_seq не опережает данные», «дыры совпадают с реальными разрывами seq».

## Стоимость и риски
- Деньги 0. Фид: 2–3 коротких сессии записи по 5 мин с одного IP.
- Риск: тихая потеря данных при неверной обрезке — поэтому оборванный хвост сохраняется в `_torn/`, а не удаляется.
