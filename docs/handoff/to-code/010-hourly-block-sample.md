## Что сделать
1. Список блоков: для каждого часа с 2026-08-04 00:00 UTC по 2026-09-30 23:00 UTC — первый блок с `timestamp` ≥ начала часа (~1 390 блоков). Номера — интерполяцией по опорным точкам из 006 + уточнение; на поиск ≤ 300 вызовов.
2. Для каждого блока: `eth_getBlockByNumber(n, true)` + `eth_getBlockReceipts(n)`. Можно через enricher (`--from n --to n`) или своим скриптом в `analytics/` — главное, чтобы сырьё сохранилось: `data/samples/hourly-20260804-20260930.jsonl.zst` (формат строки как у `blocks-*.jsonl.zst`, по строке на блок).
3. Показатели по каждому блоку (таблица `data/samples/hourly-metrics.tsv`): время, день недели, час UTC; tx без `0x6a`; свопы v3/v4; откаты; `gasUsed`; base fee; число tx с `gasUsedForL1 > 0` и медиана комиссии; сырой размер block/receipts и размер строки после zstd-3.
4. Сводка в отчёте:
   - средние и p10/p50/p90 по всему периоду для КБ/блок (файл), tx/блок, свопов/блок, доли откатов;
   - профиль по часам UTC (24 точки) и по дням недели (7 точек);
   - по дням 20.09–30.09: base fee, доля `gasUsedForL1 > 0`, медиана комиссии — есть ли скачок после 29.09;
   - пересчёт: диск под историю с 04.08 (на 07.10 и 14.10), поток новых блоков ГБ/сут — с интервалами, а не одной цифрой;
   - сравнение с 4 окнами 006: в какой части распределения они лежат.
5. Факты с датой — в `chain-facts.md` (только то, что прямо измерено).

- Не делать выводов «стоит/не стоит грузить историю» — только цифры; выводы — skeptic-analyst и Cowork.
