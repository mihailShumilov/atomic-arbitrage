# 006 — Цифры для решения по истории + перепроверка фактов прежней сессии
status: ready
phase: 1a
depends-on: 003
executor: indexer-engineer (замеры), infra-ops (цены провайдеров и ноды)
reviewers: data-auditor

## Зачем
Решения 0001 (история) и 0002 (провайдер) не принять без цифр: сколько весит блок с чеками, сколько вызовов и денег стоит окно истории, хранит ли снапшот ноды чеки. Заодно — вернуть в скилл факты, измеренные потерянной сессией, но уже как собственные измерения.

## Контекст
- `docs/decisions/0001-history-backfill.md`, `0002-rpc-provider.md`.
- Порядок величин: ~10 блоков/с → ~864 000 блоков/сутки; окно 3–4 недели ≈ 18–24 млн блоков; с запуска Pons v2 (04.08.2026) до 30.09 ≈ 49 млн блоков.
- Факты прежней сессии (гипотезы до перепроверки): 9.91–10.2 блока/с; ~9.5 tx/блок; ~3.2 свопа/блок; 7.9% откатившихся tx на 200 блоках; ~1.9 ГБ сырого фида/сутки; фид сам закрывает соединение; 429 при частых переподключениях; бан ~1 ч; `eth_getBlockReceipts` отдаёт откатившиеся tx и для старых блоков.

## Что сделать
1. **Выборка блоков** (публичный RPC или ключ провайдера, если Михаил дал): 5 окон по 200 блоков — вчера, 1 неделю назад, 3 недели назад, ~04.08.2026, ~01.07.2026. Для каждого окна: tx/блок (без системной), свопов/блок (v3+v4 topic0), доля `status=0`, байт `eth_getBlockReceipts` и `eth_getBlockByNumber(full)` на блок (сырой JSON и zstd-3), доля блоков без пользовательских транзакций.
2. **Старые блоки**: работает ли `eth_getBlockReceipts` на блоках ≥ 2 месяцев назад на публичном RPC и у провайдера; есть ли откатившиеся tx в ответе.
3. **Экстраполяция**: вызовы, байты (сырые и zstd), время при 50/200/500 rps для окон 3 нед., 4 нед. и «с 04.08».
4. **Провайдеры** (infra-ops, по официальным страницам цен, с датой и ссылкой): QuickNode и Chainstack для Robinhood Chain — поддерживается ли сеть, цена/кредиты за `eth_getBlockReceipts`, `eth_getBlockByNumber`, `eth_getLogs` (лимит диапазона), `debug_traceBlockByNumber`; лимиты rps на тарифах; стоимость 20 млн и 50 млн блоков по вариантам. Если тестовый ключ есть — замерить реальный rps и доступность `debug_traceBlock*` на 10 блоках.
5. **Временная нода** (infra-ops): есть ли официальные снапшоты Robinhood Chain (Nitro), размер, pruned или archive, есть ли в pruned чеки старых блоков (по документации Nitro/Orbit и, если возможно, по описанию снапшота); требования к железу; оценка времени синхронизации; стоимость на i4i.2xlarge/i4i.4xlarge за нужный срок.
6. **Фид** (без специальных экспериментов): по записи из 001/002/004 — ГБ/сутки (если есть ≥ 6 ч записи), частота закрытий соединения сервером, коды.
7. Каждый подтверждённый пункт добавить в `references/chain-facts.md` в формате «[проверено ДАТА] … (как)». Неподтверждённое — не добавлять, перечислить в отчёте.

## Что НЕ делать
- Не покупать тарифы и не заводить платные ноды — только цены и тестовые ключи, если Михаил их дал.
- Публичный RPC: не больше 3 000 вызовов, `--rps` ≤ 5.
- Не провоцировать баны фида ради проверки факта о бане.

## Критерии приёмки
- Таблица по 5 окнам с цифрами; экстраполяция на 3 варианта окна; таблица цен со ссылками и датой.
- Ответ «да/нет/неизвестно + почему» на вопрос о чеках в снапшоте.
- data-auditor подтверждает методику подсчёта (что считается свопом, откатом, системной tx).
- В `chain-facts.md` добавлены проверенные факты с датами.

## Стоимость и риски
- ≤ 3 000 вызовов публичного RPC; деньги 0.
- Риск: малая выборка (1 000 блоков) — в отчёте указать разброс между окнами.

## Формат отчёта
Сделано; таблицы; что подтверждено/опровергнуто из списка фактов прежней сессии; открытые вопросы для решения 0001/0002.
